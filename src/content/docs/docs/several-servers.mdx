An app can run on more than one server. Each extra server runs the same image with the same number of replicas. The app's own server spreads visitors over all of them.

## How it works

Visitors arrive at the app's own server, through its public IP or its Cloudflare Tunnel. Its proxy sends each visitor to one replica, on that server or on an extra one. Traffic to the extra servers goes through a private network.

- **DNS** points at the app's own server only. The extra servers need no DNS records and no open ports.
- **HTTPS** is handled by the app's own server. It holds the certificates.
- **No public IP?** If the app's own server has no public IP (a home server behind a router, for example), give the app's domains a Cloudflare Tunnel. The settings page warns you when you need one.

If the app's own server goes down, the app is down too, even when the extra servers still run. This is the usual setup with one load balancer in front of several app servers. To bring the app back, make an extra server the main one (see below).

## Change the main server

The app's own server is its main server. Visitors enter through it. You can make another server the main one at any time, without a redeploy:

- In **Settings → Servers & registry**, click **Make main** next to an extra server.
- Or, on the **Domains** tab, click **Change** next to **Visitors enter through**.
- When you add a domain, you can also pick the server under **Visitors enter through**.

A server can only take visitors when its proxy runs, it has a public IP or a Cloudflare Tunnel, and it runs the current version of the app. Serve says so when one of these is missing.

When you switch, Serve:

1. Copies the HTTPS certificates to the new main server (nginx). Caddy and Traefik get their own.
2. Gives the new main server the load balancing. The old one stays as an extra server.
3. Points the domain's A record at the new server, when the domain's zone is in a connected Cloudflare account. This works for records Serve made and for your own: your own record is changed only when it pointed at the old main server, and it keeps its proxy (orange cloud) setting. Tunnel domains move to the new server's tunnel of the same Cloudflare account.
4. Tells you which domains you must point at the new IP yourself: when your DNS is somewhere else, or your record pointed somewhere other than the old main server. Until you do, those visitors still reach the old server, which serves its own replicas only.

Serve refuses the switch when a domain would stop working, for example a tunnel domain when the new server has no tunnel of that Cloudflare account and no public IP.

## Set it up

1. Put the servers in a [private network](/docs/private-networks).
2. Open the app's **Settings → Servers & registry**.
3. Tick the extra servers. **Load balance visitors across these servers** turns on with the first one.
4. Click **Save and deploy**.

Each extra server shows how it takes part:

| Badge | Meaning |
| --- | --- |
| **Gets traffic** | All its replicas get visitors. |
| **Gets traffic (1/2)** | Some replicas do not answer. The others get visitors. |
| **No traffic: no private network** | The server has no private network with the app's own server. |
| **Joining the private network** | The server is getting its private addresses. This takes a few seconds. |
| **No traffic until deployed** | Deploy the app to start using the server. |
| **No traffic: deploy failed** | The last deploy failed there. The server keeps the older version and gets no visitors. |
| **No traffic: not answering** | Its replicas do not answer. Serve tries again every few seconds. |

Turn the switch off to keep the extra servers running the app without sending them visitors, for example behind a load balancer of your own.

Two servers are enough to start. Add more when you need more capacity.

## Health and failures

Serve checks every replica on the extra servers every 5 seconds, from the app's own server. A replica that fails two checks in a row gets no visitors until it passes two checks again. If you set a health check path (**Settings → Health check**), Serve loads that path. Otherwise it checks that the port answers.

A visitor that reaches a replica that just died is retried on another replica. The one exception: a request already in flight when a whole server goes down can fail.

An error from your app, like a 500 page, does not take a replica out. Only replicas that do not answer are taken out.

## Load balancing strategy

Pick how visitors are spread in **Domains & ports → HTTP options → Load balancing**:

| Strategy | What it does |
| --- | --- |
| **Round robin** | Each replica gets visitors in turn. This is the default. |
| **Least busy** | Each visitor goes to the replica with the fewest open requests. Good for slow requests, like uploads or streams. |
| **Sticky sessions** | A visitor keeps reaching the same replica. Use it for Socket.IO or sessions kept in memory. |
| **Main server first** | Only the main server's replicas get visitors. When none of them answers its health check, the extra servers take the visitors until the main server is back. |

With **Main server first**, Serve also checks the main server's own replicas every 5 seconds. The switch to the extra servers, and back, takes about 10 seconds. The extra servers show **Standby** in **Settings → Servers** while they wait.

If the domain's DNS points at an extra server instead of the main one, the domain shows **Points to** and that server's name. That server only serves its own replicas. Point the record at the main server, or make that server the main one.

## Deploys

The app's own server deploys first. If that fails, the deploy fails and every server keeps the old version. Then the extra servers deploy at the same time. Each one keeps serving its old version until its new replicas are healthy.

A server whose deploy fails keeps its old version and gets no visitors until a deploy succeeds there. The deploy log names it.

## Images

A Git, Dockerfile or upload app is built once. Without a registry, Serve copies the image from the build server to each extra server, so every server runs the exact same image. With a registry (**Settings → Servers & registry**), each server pulls the image instead. That is faster for big images and many servers. An image only runs on the CPU type it was built for. So when the app runs on servers of another CPU type (ARM servers next to Intel or AMD ones), one of those servers builds the image from the same commit, at the same time as the main build. The other servers of that type copy the image from it. With two ARM and two AMD servers, there are two builds side by side, and the other two servers only copy.

An app from a Docker image is pulled on each server.

## Replicas

Each server runs the number of replicas set in **Settings → Runtime**. With 3 servers and 2 replicas, 6 containers run.

Replica numbers continue across servers, so `SERVE_REPLICA_INDEX` goes from 0 to 5 in that example. Use it to give each replica its own shard or task. See [Per-replica variables](/docs/environment-variables#per-replica-variables).

## Logs, console and metrics

- **Logs** shows every server's replicas. Pick one replica from the dropdown, for example **hetzner-1 · Replica 2**.
- **Console** lists every replica, with its server.
- **Overview** counts and lists the replicas of every server.
- **Metrics** adds up CPU, memory and network over every server that collects metrics. Turn on metrics on each server's **Metrics** page.

## Data

Each server has its own volumes. Nothing is shared or synced between servers, so keep state in a database. A pre-deploy command runs once, on the app's own server.
