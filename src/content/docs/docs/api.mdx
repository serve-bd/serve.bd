The Serve API lets you do from a script or CI what you do in the dashboard: create services, deploy, set variables, add domains, back up databases and more. It speaks JSON over HTTPS.

## Make a token

1. In the dashboard, open **Keys & tokens** and choose **Create API token**.
2. Give it a name and pick what it may do. Start from a preset and add or remove permissions:

   | Preset | Permissions |
   | --- | --- |
   | **Read only** | `projects.view`, `logs.view` |
   | **Deploy** | Read only, plus `services.deploy` |
   | **Manage services** | Deploy, plus `services.manage`, `variables.edit`, `domains.manage` |
   | **Admin** | Everything (`admin`) |

3. Pick all projects or only some, and when the token expires.
4. Copy the token. It starts with `srv_` and is shown only once.

## Your first request

Every request goes to `https://<instance>/api/v1` and sends the token as a bearer token. Put both in your shell:

```bash
export SERVE_URL=https://serve.example.com/api/v1
export SERVE_TOKEN=srv_...
```

Ask the API who the token is:

```bash
curl "$SERVE_URL/me" -H "Authorization: Bearer $SERVE_TOKEN"
```

```json
{
  "token": { "id": "...", "name": "CI", "granted": ["projects.view", "logs.view", "services.deploy"] },
  "user": { "...": "..." },
  "organization": { "...": "..." },
  "permissions": ["projects.view", "services.deploy", "logs.view"],
  "admin": false,
  "projectIds": null
}
```

`permissions` is what the token may do right now. `projectIds` is `null` when it reaches every project.

## Permissions

A token carries the same permissions that roles are made of:

| Permission | Lets the token |
| --- | --- |
| `projects.view` | See projects, services, deployments and their status |
| `projects.manage` | Create, rename and delete projects and environments |
| `services.deploy` | Deploy, redeploy, roll back, start, stop and restart services |
| `deploys.approve` | Approve or reject deploys that wait for approval |
| `services.manage` | Create and delete services and change their settings |
| `domains.manage` | Add, edit and remove domains, ports and proxy options |
| `variables.edit` | Add, change and delete environment and shared variables |
| `variables.view-secrets` | Reveal secret variables, database passwords and connection URLs |
| `databases.backups` | Run, download, restore and import database backups |
| `console.access` | Open a shell inside containers and servers |
| `logs.view` | Read build, runtime and request logs |
| `members.manage` | Invite and remove members, change roles and project access |
| `integrations.manage` | Git providers, Cloudflare, S3, registries, notifications, templates and certificates |
| `admin` | Everything an organization admin may do, including all of the above |

Three rules:

- **A token never does more than its owner may do right now.** If the owner's role changes, the token changes with it.
- **A token limited to some projects** answers `404` for every other project, as if it did not exist.
- **Instance routes** (`/instance/...`) need an `admin` token whose owner is an admin of the Root organization.

Each endpoint in the reference shows the permissions it needs.

## Errors

Errors are JSON with a message:

```json
{
  "error": "This token cannot do this. It needs: services.deploy (Deploy). A token never has more than its owner's role allows.",
  "missing": ["services.deploy"]
}
```

| Status | Means |
| --- | --- |
| `400` | The body is wrong. The message names the field. |
| `401` | The token is missing, wrong or expired. |
| `403` | The token lacks a permission. `missing` lists what it needs. |
| `404` | Not found, or not in the token's projects. |
| `405` | Wrong method. The `Allow` header lists the right ones. |
| `409` | Conflict, such as a name already in use or a deploy in progress. |
| `413` | The body is larger than 10 MB. |
| `429` | Too many requests for this token. Wait the seconds in the `Retry-After` header. |
| `503` | An admin turned the API off. |

### Rate limit

Each token may make 200 requests per minute by default. Every response carries the `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers. An admin changes the limit, or turns the API off, under **Settings → Security**. See [Security](/docs/security#api-access).

## Common tasks

### Find a project and its services

```bash
curl "$SERVE_URL/projects" -H "Authorization: Bearer $SERVE_TOKEN"
curl "$SERVE_URL/projects/$PROJECT_ID" -H "Authorization: Bearer $SERVE_TOKEN"
```

The project comes with its `environments` and `services`. New services need a `projectId` and an `environmentId`.

### Create an app

From a Docker image:

```bash
curl -X POST "$SERVE_URL/services" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "app",
    "projectId": "<projectId>",
    "environmentId": "<environmentId>",
    "name": "web",
    "source": { "type": "image", "image": "nginx:alpine" },
    "port": 80,
    "deploy": true
  }'
```

From Git, use `"source": { "type": "git", "repository": "acme/web", "branch": "main" }`. The answer is `201` with the new service's `id`.

### Create a database

```bash
curl -X POST "$SERVE_URL/services" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "type": "database", "projectId": "<projectId>", "environmentId": "<environmentId>", "name": "db", "engine": "postgres", "deploy": true }'
```

`engine` is one of `postgres`, `mysql`, `mariadb`, `mongodb`, `redis`, `valkey` or `clickhouse`.

### Create a service from a template

List the templates with `GET /templates`, then create a compose service with the template's id. Secrets you leave out are generated.

```bash
curl -X POST "$SERVE_URL/services" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "type": "compose", "projectId": "<projectId>", "environmentId": "<environmentId>", "name": "n8n", "template": "n8n", "deploy": true }'
```

### Deploy and wait for it

```bash
curl -X POST "$SERVE_URL/services/$SERVICE_ID/deploy" -H "Authorization: Bearer $SERVE_TOKEN"
# 202 { "deploymentId": "..." }

curl "$SERVE_URL/deployments/$DEPLOYMENT_ID" -H "Authorization: Bearer $SERVE_TOKEN"
```

Poll the deployment until its `status` is `success`, `failed` or `cancelled`. It also returns the end of the build log as `logTail`.

### Set variables

Set some keys and remove others with `null`. Variables you leave out stay as they are.

```bash
curl -X PATCH "$SERVE_URL/services/$SERVICE_ID/variables" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "variables": { "API_URL": "https://api.example.com", "OLD_KEY": null }, "redeploy": true }'
```

### Add a domain

```bash
curl -X POST "$SERVE_URL/services/$SERVICE_ID/domains" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "hostname": "app.example.com" }'
```

The domain gets HTTPS with a free certificate. Point its DNS at your server first.

### Get database connection details

```bash
curl "$SERVE_URL/services/$SERVICE_ID/connection" -H "Authorization: Bearer $SERVE_TOKEN"
```

You get the host, port, user and database. Passwords and URLs are included only when the token has `variables.view-secrets`.

### Back up and restore

```bash
curl -X POST "$SERVE_URL/services/$SERVICE_ID/backups" -H "Authorization: Bearer $SERVE_TOKEN"
curl "$SERVE_URL/services/$SERVICE_ID/backups" -H "Authorization: Bearer $SERVE_TOKEN"

curl -X POST "$SERVE_URL/backups/$BACKUP_ID/restore" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "backupFirst": true }'
```

`backupFirst` backs up the current data before the restore.

### Read logs

```bash
curl "$SERVE_URL/services/$SERVICE_ID/logs?tail=200" -H "Authorization: Bearer $SERVE_TOKEN"
```

`tail` is the number of lines per container, from 10 to 5000.

### Approve a deployment

In an environment that needs approval, a deployment waits with the status `waiting`. A token with `deploys.approve` lets it go, or rejects it:

```bash
curl -X POST "$SERVE_URL/deployments/$DEPLOYMENT_ID/approve" -H "Authorization: Bearer $SERVE_TOKEN"

curl -X POST "$SERVE_URL/deployments/$DEPLOYMENT_ID/reject" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "reason": "Wait for the migration on Monday" }'
```

Both answer the deployment. The `reason` is optional, up to 500 characters, and shown with the deployment. Approval answers `409` when the deployment no longer waits, or while deploys are frozen.

### Run a command in a container

```bash
curl -X POST "$SERVE_URL/services/$SERVICE_ID/exec" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "command": "ls -la /app" }'
```

This needs `console.access`. The command runs with `sh -c` and the output streams back as plain text, standard output and errors together. The last line is a NUL character followed by the exit code. A command stops after 15 minutes. `target` picks a compose service or container, and `replica` a replica by its number. `GET /services/{id}/exec` lists the containers you can pick.

### Make a token from a script

```bash
curl -X POST "$SERVE_URL/tokens" \
  -H "Authorization: Bearer $SERVE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Preview CI", "scopes": ["projects.view", "services.deploy"], "expiresInDays": 30 }'
```

Any token can make a token for the same person, with the same rules as **Keys & tokens**: never more permissions or projects than the token that asks. A token that expires only makes tokens that expire no later. The answer is `201`, and holds the new secret once.

## Console and more

### Shells

`POST /services/{id}/terminal` opens a shell in a container, and `POST /servers/{id}/terminal` a root shell on a server. Both take `cols` and `rows` (80 by 24 when left out), and `command` to run one command with a terminal instead. They answer `201` with the session's `id`. Then:

- `GET .../terminal/{sessionId}` is a Server-Sent Events stream. Each `data` event holds base64 output, with its number as the event id. An `exit` event, `{"code": n}`, ends it. `since`, or the `Last-Event-ID` header, replays what you missed.
- `POST .../terminal/{sessionId}` takes `{"type": "input", "data": "ls\r"}` or `{"type": "resize", "cols": 120, "rows": 40}`, and answers `204`. These don't count against the rate limit.
- `DELETE .../terminal/{sessionId}` closes the shell. A shell nobody listens to closes after a minute.

Both need `console.access`. A shell on a server also needs `admin`, from an admin who manages the server. A service with host access, like bind mounts or privileged mode, needs an admin of the Root organization.

### Servers and networking

- **Tailscale:** `GET /tailscale/tailnets`, and `GET`, `DELETE`, `POST .../join-command` and `POST .../connect` under `/servers/{id}/tailscale`. These are instance routes, for admins of the Root organization. See [Tailscale](/docs/tailscale).
- **Private networks:** `GET` and `POST /private-networks`, `PATCH` and `DELETE /private-networks/{id}`, and `PUT /private-networks/{id}/members` with `{ "serverId", "member" }`. They need `admin`. A server must have joined the private network from its page first. See [Private networks](/docs/private-networks).
- **Cloudflare Tunnels:** `GET` and `POST /cloudflare/accounts/{accountId}/tunnels`, and `DELETE .../tunnels/{tunnelId}`. `GET /cloudflare/accounts/{accountId}/zones/{zoneId}/dns` lists a zone's records. They need `integrations.manage`.
- `GET /servers/{id}` also returns `setupLog`, `alerts` and `proxySwitch`, but only to an `admin` token whose owner is an admin who manages that server. A server shared from another organization stays read only.
- `DELETE /servers/{id}` takes `services=stop` or `services=keep`, and `removeData`, `removeProxy`, `removeTunnels` and `removeTailnetDevice`. A server with services needs `services`.

### Log drains and other changes

- **Log drains:** `GET` and `POST /log-drains`, `PUT` and `DELETE /log-drains/{id}`, and `POST /log-drains/{id}/test`. They need `integrations.manage`. Header values and passwords are never returned. See [Log drains](/docs/log-drains).
- `GET /notification-channels/types` lists the kinds of notification channels with their fields, and the events.
- `GET /services/{id}/monitor` returns the uptime check in the shape `PUT` takes, with its status.
- `GET /templates` also lists your organization's own templates, with `custom: true` and the id `custom:<id>`.
- `POST /services/{id}/webhook-secret` answers the new `deployHookUrl` too. The secret is hidden without `variables.view-secrets`.
- `PATCH /tasks/{id}` without `enabled` keeps a paused task paused.

## Older endpoints

Scripts written for earlier versions keep working:

- `GET` and `PATCH /services/{id}/env`
- `POST /services/{id}/deploy`, `/start`, `/stop` and `/restart`
- `GET /deployments/{id}`

Older tokens keep their scopes. Each one now means a set of permissions:

| Old scope | Permissions |
| --- | --- |
| `read` | `projects.view`, `logs.view` |
| `read:sensitive` | `read`, plus `variables.view-secrets` |
| `deploy` | `read`, plus `services.deploy` |
| `write` | `deploy`, plus `services.manage`, `variables.edit`, `domains.manage` |
| `admin` | `admin` |

To deploy from CI without a token, you can also use a [deploy hook](/docs/deployments/).
