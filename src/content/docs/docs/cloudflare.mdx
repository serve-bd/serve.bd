Connect a Cloudflare account to manage DNS records, SSL modes and certificates from the dashboard. Cloudflare Tunnels let you serve apps from servers without a public IP or open ports.

## Connect an account

Go to **Integrations → Cloudflare** and choose **Connect Cloudflare**. There are two ways to connect.

### Sign in with Cloudflare

Choose **Sign in with Cloudflare**, log in to Cloudflare, pick the account with your domains and allow access. You return to Serve with the account connected.

- Cloudflare returns you through a page on `serve.bd`, which sends your browser back to the dashboard you started from. So a dashboard on a private address works too. The page never sees a usable token.
- The first time in a browser, the page asks you to confirm your dashboard's address before it goes on to Cloudflare. Only continue if it is your own dashboard: anyone can make a link that would connect your Cloudflare account to their server.
- The sign-in has to start and end in the same browser, within 30 minutes.
- Serve renews the access by itself. If you remove Serve's access in Cloudflare (**My Profile → Manage OAuth authorizations**), the account shows an error with a **Reconnect** button.
- Traefik's Cloudflare DNS challenge needs an API token, because Traefik keeps its token for months.
- An administrator of a Cloudflare account can block outside apps. Then paste an API token instead.

### Use your own OAuth client

**Sign in with Cloudflare** uses Serve's OAuth client by default. To use your own client instead, for example so that sign-ins skip `serve.bd`, create one in Cloudflare:

1. Go to **Manage Account → OAuth clients → Create client**.
2. Set these fields:

   | Field | Value |
   | --- | --- |
   | Response type | Code |
   | Grant type | Authorization Code and Refresh Token |
   | Token authentication method | None (PKCE) |
   | Redirect URL | `https://<your dashboard>/api/cloudflare/oauth/callback` |

3. Select these scopes, all required:

   | Scope | Id |
   | --- | --- |
   | Zone Read | `zone.read` |
   | DNS Write | `dns.write` |
   | Zone Settings Write | `zone-settings.write` |
   | SSL and Certificates Write | `ssl-and-certificates.write` |
   | Cloudflare Tunnel Write | `argotunnel.write` |
   | Cloudflare One Connectors Write | `teams-connectors.write` |

   Without **Refresh Token**, the access ends after an hour.

4. Add these lines to `/data/serve/.env`:

   ```bash
   CLOUDFLARE_OAUTH_CLIENT_ID=<the client id>
   CLOUDFLARE_OAUTH_REDIRECT_URI=https://<your dashboard>/api/cloudflare/oauth/callback
   ```

5. Restart Serve with `cd /data/serve && docker compose up -d`.

The redirect URL must match exactly, with the address you open the dashboard at. A client stays private unless you make it public, and a private client only lets members of your own Cloudflare account sign in. That is enough for your own instance.

`CLOUDFLARE_OAUTH_SCOPES` replaces the scope list, separated by spaces. Leave it unset unless your client has other scopes. Serve adds no scopes to it, so include `offline_access` to keep a refresh token.

### Paste an API token

Paste an **API token** from your Cloudflare dashboard. Serve encrypts the token and only uses it for your zones.

Give the token these permissions:

| Type | Permission | Access |
| --- | --- | --- |
| Zone | Zone | Read |
| Zone | DNS | Edit |
| Zone | Zone Settings | Edit |
| Zone | SSL and Certificates | Edit |
| Account | Cloudflare Tunnel | Edit (only to use tunnels) |

The **Origin CA key** field is optional. You only need it if your token cannot create origin certificates.

If you disconnect an account, existing DNS records stay in Cloudflare. Certificates that use the account stop renewing.

### Several accounts

A sign-in or a token can reach several Cloudflare accounts. Each account gets its own entry, with its own domains and tunnels, and they share the login: renewing it or choosing **Reconnect** fixes all of them. Disconnecting one keeps the others; the login goes, and its access in Cloudflare ends, once no account uses it.

With one account, the Cloudflare page shows that account directly. With several, it lists them, and each opens its own page.

Signing in again to an account that is already connected moves it to the new login, with its tunnels, domains and certificates. An account connected with a pasted API token keeps that token.

## DNS records

Each zone shows its DNS records. You can add, edit and delete records, filter by type and search. A record has a type (such as `A`, `AAAA` or `CNAME`), a name, content, a TTL and a **Proxied** switch. Proxied means traffic goes through Cloudflare (orange cloud). **DNS only** means it does not.

When you add a domain to a service, tick **Create the DNS record** and Serve creates the record for you. See [Domains](/docs/domains).

For a proxied record, the DNS check reads the record through the connected account, because public DNS only shows Cloudflare's addresses. The check passes when Cloudflare forwards to the server's IP. It fails and shows the real target when Cloudflare forwards somewhere else. If no connected account manages the zone, the check stays a warning. This applies to the dashboard domain check and to the DNS badges on service domains.

## SSL mode

You can change the zone's **SSL/TLS mode** from Serve. The change takes effect in Cloudflare immediately.

| Mode | Meaning |
| --- | --- |
| Flexible | HTTPS to Cloudflare, HTTP to your server. |
| Full | HTTPS end to end, any certificate. |
| Full (strict) | HTTPS end to end with a valid certificate. Recommended. |

You can also turn on **Always use HTTPS** to redirect HTTP requests at the edge, and **Purge cache** to clear everything cached at Cloudflare.

## Tunnels

A Cloudflare Tunnel serves domains from a server without a public IP or open ports. The server connects out to Cloudflare, and Cloudflare handles HTTPS.

1. On the Cloudflare account page, choose **Create tunnel** next to the server. It connects within a minute.
2. On a service's domain, set **Route traffic through** to the tunnel.

The tunnel page lists the **Domains through this tunnel** and the connector's status. If the connector stops, you can restart it from there. **Remove tunnel** stops the connector and deletes the tunnel in Cloudflare.

:::note
Tunnel domains are HTTPS at Cloudflare even though the proxy on your server serves them over HTTP. `SERVE_PUBLIC_URL` uses `https://` for them.
:::

### The dashboard through a tunnel

The dashboard can use a tunnel too. This is useful when the main server has no public IP. First create a tunnel for the server Serve runs on. Then, in **Settings → General**, enter the dashboard domain and choose **Cloudflare Tunnel** instead of **Server IP**. The tunnel needs a domain: without one, the tunnel choice is cleared when you save.

### Databases through a tunnel

Since v0.2.6, new database domains can't use a Cloudflare Tunnel. A database domain set up through a tunnel before keeps working until you change or remove it. Its clients connect with `cloudflared`, which forwards a local port to the database:

```bash
cloudflared access tcp --hostname db.example.com --url localhost:5432
```

Then point your client at `localhost:5432`. The database's **Public access** page shows the exact command. For new database domains, use a server with a public IP. See [Databases](/docs/databases#database-domain).

## Wildcard certificates

Let's Encrypt can only issue wildcard certificates like `*.example.com` with DNS validation. Choose **Let's Encrypt via Cloudflare DNS** as the source on the **Certificates** page. Validation goes through your connected Cloudflare zone, so port 80 does not need to be reachable. The certificate renews automatically.

A wildcard certificate pairs well with a server's **Wildcard domain** and with pull request previews, where one wildcard DNS record covers all previews.
