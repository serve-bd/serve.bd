title: "Database backups"
description: "Scheduled backups to disk or a bucket, and one-click restore."
---

Serve backs up databases with each engine's own dump tools. You set a schedule per database on its **Backups** tab, and keep copies on the server, in a bucket, or both.

:::note[Instance backups are separate]
Database backups protect your data. They don't include Serve's own state. To back up the dashboard, certificates and settings, see [Instance backups](/docs/instance-backups). An instance backup does not include app or database data either, so you need both.
:::

## Automatic backups

Open a database, go to **Backups → Auto backup** and turn on **Automatic backups**. When it is off, backups only run when you click **Back up now**.

Under **How often**, pick one of:

- **Hourly**: every 1, 2, 3, 4, 6, 8 or 12 hours, at a chosen minute.
- **Daily**: at a time of day.
- **Weekly**: on chosen days, at a time of day.
- **Custom**: a **Cron expression**, like `0 3 * * *`.

Times use the instance timezone. Change it in **Settings → General**.

### Time limit and CPU priority

- **Time limit**: in minutes. A backup that runs longer is stopped and marked failed. It applies to **Back up now** too. Limits longer than 6 hours work.
- **Low CPU priority**: the dump and its compression run with `nice 19`, so apps get the CPU first. Backups take longer.

### How many to keep

Older backups are deleted automatically. When you keep backups in one place, **Keep the latest** sets how many copies stay there. When you keep them in both, **Keep on this server** and **Keep in bucket** set each one. Keep more in the bucket for longer off-site history.

**Keep longer** keeps more on top of the latest ones (for the bucket copies when you use a bucket):

- **All from … days**: every backup younger than that.
- **1 a day / week / month / year for …**: the newest backup of each of the last days, weeks, months or years.

A backup is kept when any rule wants it. Backups taken [before a deploy](#back-up-before-each-deploy) are counted on their own, so they never push out the scheduled ones.

### Where backups are stored

**Store backups in** picks where copies are kept: on this server, in a bucket, or both. Both is the default when you have a bucket.

- **This server**: kept in the data directory. These copies are lost if the server is lost.
- A bucket you added under **Integrations → S3 storage**. Any S3-compatible store works, like R2 or B2.

With the bucket only, each copy leaves the server once it is uploaded. A restore downloads it first.

Pick more than one bucket to keep a copy in each, for example in two clouds. The first bucket you pick is the main one. Downloads and restores use the next bucket when one is down, and cleanup removes old backups from every bucket.

### Compression, checksums and encryption

- Backups are compressed. MySQL, MariaDB and ClickHouse dumps are `.sql.gz`.
- Each backup has a SHA-256 checksum recorded when it is made. Serve checks it before every restore, so a file damaged on disk or in a bucket stops the restore before anything changes. Downloads send it in the `X-Checksum-SHA256` header.
- **Encrypt backups** encrypts each backup with a passphrase you choose, before it is stored or uploaded. Serve decrypts it when restoring. The file ends in `.enc` and also opens without Serve:

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 -in backup.sql.gz.enc -out backup.sql.gz
```

:::caution
Keep the passphrase somewhere safe. Without it, nobody can restore encrypted backups. When you change it, older backups keep the passphrase they were made with, and a restore asks for it.
:::

### Include users and passwords

For PostgreSQL, MySQL and MariaDB, **Include users and passwords** makes each backup also save the server's database users, their passwords and their rights. Without it, a backup holds only your data. A restore brings the users back only when you check **Also restore the dump's users and passwords**. Serve's own accounts never change. MongoDB backups always include their users.

### Test backups daily

**Test backups daily** restores the newest backup each day into a throwaway database of the same image, on the same server and without network access. Serve counts what came back (tables, collections or keys), shows **Tested** on the backup, and removes the throwaway database. If a test fails, you get a **Backup test failed** notification. You can also test any backup from its **⋯** menu with **Test restore**.

### Back up before each deploy

In an app's **Settings → Deploy**, **Back up before each deploy** picks databases of the environment to back up before each deploy, before the pre-deploy command (your migrations). If a backup fails, nothing is deployed. Rollbacks skip it.

## S3 storage

Add a destination under **Integrations → S3 storage**. Serve supports **Amazon S3**, **Cloudflare R2**, **Backblaze B2**, **DigitalOcean Spaces**, **Wasabi**, **MinIO** and **Other S3-compatible**.

| Field | What it is |
| --- | --- |
| Endpoint | The S3 API URL of the provider |
| Region | The bucket's region |
| Bucket | The bucket name |
| Path prefix | A folder inside the bucket for Serve's backups |
| Access key ID | The key ID |
| Secret access key | The secret for the key |

Serve checks that it can write to the bucket before it saves the destination.

:::tip
Give Serve a key that can only access its own bucket.
:::

## Running and restoring

The **Backups** list shows every backup. From it you can:

- **Back up now**: take a backup right away. The database must be running. The window is filled in from the backup settings: where it is stored, whether it includes users and passwords, and whether it is encrypted. Changes there are for that backup only.
- Download a backup file.
- Restore a backup.
- Test a backup.
- Delete a backup.

### Restore

**Restore** opens a window where you choose:

- **Restore into**: this database, or another database service of the same kind, for example last night's production backup into staging.
- **Databases**: which databases of the backup to restore, and **Restore as** to give one a new name.
- **Tables**: **All tables**, or **Only some tables** of one database (PostgreSQL, MySQL, MariaDB). Those tables are replaced and the others stay as they are.
- **Back up first**: takes a backup of the target first. If it fails, nothing is restored.
- **Databases keep their names.** A dump of `ecommerce` restores into `ecommerce`, not into the main database. If your app should connect to it, open **Settings → Credentials**, choose **Use another** and pick it. The connection URL and `${{name.DATABASE_URL}}` then name it.
- **Also restore the dump's users and passwords** (PostgreSQL, MySQL, MariaDB, MongoDB): only when you move a whole server. The old accounts come back with their passwords and rights. Serve's own accounts keep theirs.

A backup keeps its database names when restored: a dump of `shop` goes back into `shop`, and empty databases in it are created too. On MySQL and MariaDB, the account apps connect with gets access to the databases a restore creates. On PostgreSQL, the dump's roles are created without login even when you leave users out, so row-level security policies that name them still work.

You get a notification when a restore or import finishes or fails.

### Choose the databases

A PostgreSQL, MySQL, MariaDB or MongoDB server can hold more than one database. You choose which ones a backup takes:

- **Back up now** asks which databases to take, when the server has more than one.
- For automatic backups, set **Databases to back up**. Tick **Every database**, or single ones. The choice shows even when the server has one database.

**Every database** means every database on the server when the backup runs, so databases you create later are included. To skip some, open **Leave some out** under **Every database** and tick the ones to skip. If you tick databases one by one instead, the backup takes only those. There is no limit on how many databases a backup takes.

On PostgreSQL, the built-in `postgres` database is offered like the others, because apps often keep their tables there. **Every database** takes it too.

Without a choice, a backup takes the main database. On MongoDB, it takes every database, and with **Every database** it takes the usual full dump.

:::note[Schedules saved before v0.2.4]
These schedules keep the list of names they had. To include databases created later, tick **Every database** again and save. In the [API](/docs/api), `"databases": ["*"]` means every database.
:::

A backup with several databases is one file. Restoring it brings back each database as it was, and creates the ones that are missing.

### Import a backup

Use **Import backup** to restore a dump made elsewhere, for example when you move from another host. You can:

- Drop a dump file in the dashboard, up to 20 GB.
- Give a **File URL**: a public or pre-signed http(s) link. The server downloads it.
- Choose **From bucket**, pick a saved **Storage** and give the **Object path** of the file inside the bucket.

The card lists which file types the engine accepts. An encrypted file (`.enc`) asks for its passphrase. Compose stacks have the same card on each backup: a dump for a database container, or a `.tar.gz` for a volume or folder.

:::caution
Restoring replaces the data in the database. Take a fresh backup first if you may need the current data.
:::

## Compose stacks and apps

Compose stacks get backups per container: PostgreSQL, MySQL, MariaDB, MongoDB, Redis, Valkey and ClickHouse. On the stack's **Backups** tab, Serve suggests the databases it finds in the stack. Click **Back up** with the database name to dump it on a schedule. You can also add storage backups, which copy volumes and folders.

Apps can have storage backups too, which copy the app's volumes and folders on a schedule. Each backup has its own schedule, keep counts and destination, like a database backup. Only admins can add them.

## API and CLI

Everything here works from the [API](/docs/api) and the [CLI](/docs/cli) too: `serve db backups restore` (with `--into`, `--database`, `--as`, `--table`, `--passphrase`), `serve db backups test`, `serve db backups download`, `serve db backups settings`, and `serve db import ./dump.sql.gz` to upload a file.
