Serve can deploy to more machines than the one it runs on. Add a server over SSH, or join a machine behind NAT with a one-line command, and Serve installs everything it needs.

## Add a server

Go to **Servers → Add server**. Serve asks **Where is the server?** and offers two choices:

- **Public IP or hostname**: a VPS or any machine reachable over SSH.
- **No public IP**: home or office internet, a shared IP, or a machine behind NAT.

### Public IP or hostname

Serve connects over SSH. Fill in these fields:

| Field | What to enter |
| --- | --- |
| **IP address or hostname** | How to reach the server. |
| **SSH port** | Its SSH port, usually `22`. |
| **User** | `root`, or a user with passwordless sudo. Serve uses it to install and run Docker. |
| **SSH key** | A key to sign in with. Generate a new one, pick a saved key or paste your own private key (OpenSSH or PEM format, without a passphrase). |

Authorize the public key on the server, for example by adding it to `~/.ssh/authorized_keys`, then choose **Connect**. Serve checks SSH access and Docker, prepares the data directory and starts the proxy. If Docker is missing, Serve can install it with the official script from get.docker.com. This takes a few minutes.

### No public IP

For a machine that nobody can reach from outside, choose **No public IP**, then **Create join command**. Serve shows a one-line command like this:

```bash
curl … | sudo bash
```

Run it on the new machine. The dashboard page moves on by itself when the server connects.

- The command works once.
- It expires after 24 hours. Create a new one if it runs out.

The server then keeps an encrypted SSH tunnel (`ssh -R`) open to the dashboard. The dashboard reaches the server through that tunnel, so the server needs no open ports.

:::caution[Open TCP port 7822]
The tunnel connects out to the main server on TCP port 7822. Open that port in the main server's firewall, and in your provider's cloud firewall if it has one. The port is set by `SERVE_TUNNEL_PORT` in `/data/serve/.env`.
:::

To give apps on such a server a public domain, use a [Cloudflare Tunnel](/docs/cloudflare).

## serve-agent

Remote servers can run `serve-agent`, a small program written in Go. It samples CPU, memory, disk, load and containers and sends them to the dashboard. When the dashboard is unreachable, the agent buffers up to a day of samples and sends them later.

Metrics are off on a newly added server. Turn them on from the server's **Metrics** page. Only an admin of the server can turn them on.

## Server pages

Each server has these pages:

| Page | What it shows |
| --- | --- |
| General | Name, connection details and status. |
| Sharing | The organization that owns the server, and the organizations it is shared with. |
| Builds & deploys | Concurrent builds, images kept, and limits for deployments. |
| Metrics | CPU, memory, disk and load over time. |
| Services | The containers running on the server. |
| Resources | Disk usage of the data directory and Docker, and the containers on the server. CPU use is a share of the whole server, so the containers add up to 100% at most. |
| Alerts | **Resource alerts** for CPU, memory and disk. |
| Docker cleanup | Clean up Docker now, and see past cleanups. |
| OS updates | Package updates for the server's operating system. |
| Domains | **Addressing** and domains on this server. See [Domains](/docs/domains). |
| Proxy | The reverse proxy: nginx, Caddy, Traefik or None. |
| Private network | The [private network](/docs/private-networks) this server is in. |
| Terminal | A shell on the server in your browser. |
| Danger zone | Remove the server. Not shown for the machine Serve runs on. |

Server IP addresses, IPv4 and IPv6, are blurred until you click them, so they stay private when you share your screen.

### Sharing

A server belongs to one organization. Only that organization deploys to it, unless a Root admin shares it with others. The **Sharing** page shows the owner and the organizations the server is shared with.

### Builds and deploys

The **Builds & deploys** page has two cards.

| Setting | What it does |
| --- | --- |
| **Concurrent builds** | How many builds the server runs at once. More need more CPU and memory. The rest wait. |
| **Images kept per service** | Each kept image allows an instant rollback. |
| **Time limit** | Deployments that run longer are stopped, and the previous version keeps running. Empty uses Serve's default. |
| **Queue size** | How many deployments may wait for this server. Empty means no limit. |

When the queue is full, a new deployment is refused, and a push or deploy hook is recorded as skipped. Rollbacks and first deploys never wait for the queue limit.

### Alerts

Samples are compared with the limits you set. **CPU duration** is the number of minutes above the limit before Serve alerts. **Disk warning** and **Disk critical** are percentages used. Crossing a limit alerts your [notification channels](/docs/monitoring). An alert clears 5 points below its limit.

### Containers Serve did not start

A server can already run containers that Serve did not start. On the **Resources** page, filter by **Unmanaged** to see them. From a container's **…** menu, you can move or copy it into a project. See [Move containers into a project](/docs/moving-containers).

## Cleanup

Docker images and build cache fill disks over time. A server's **Docker cleanup** page lets you clean up Docker now and lists past cleanups and what they freed.

The schedule for every server is set under **Settings → Advanced → Automatic cleanup** by an instance admin:

| Setting | What it does |
| --- | --- |
| **Scheduled cleanup** | Removes dangling images, stale deployment containers and old build cache on a schedule (**Run every**). |
| **Clean up when disk reaches** | Runs an aggressive cleanup when the disk fills to this level, and notifies you. |
| **Keep build cache for** | How long to keep build cache. `0` keeps it forever: faster builds, more disk. |
| **Remove unused images** | Also deletes images no container uses that are older than a day. |
| **Remove unused anonymous volumes** | Also deletes volumes without a name that no container uses. Off by default. Needs Docker 23 or newer (Docker API 1.42). |
| **Remove unused networks** | Also deletes Docker networks no container uses. Networks of stopped containers are kept. Off by default. |

:::caution[These two work on the whole server]
The volume and network options also remove volumes and networks of projects that Serve does not manage. Data in a removed volume can't be brought back. Named volumes are never removed. Serve's own networks, and networks a container uses, even a stopped one, are never removed.
:::

Without those options, volumes and running containers are never touched. Images kept for rollbacks stay.

## OS updates

The **OS updates** page lists package updates for the server's operating system. It works with apt, dnf, yum, zypper, pacman and apk. On Arch Linux, install `pacman-contrib`: Serve uses its `checkupdates` to look for updates.

- Serve checks once a week and only tells you. It sends the **Operating system updates available** notification. Choose **Check now** to look right away.
- Serve installs updates only when you ask: pick some packages, or choose **Update all**.
- Docker's packages are left out of **Update all**, because updating Docker restarts every container. Pick them on their own. On the server Serve runs on, Docker can't be updated from here, because it would stop Serve itself. Update it in a terminal on the host.
- A server connected as a user other than `root` needs passwordless sudo.
- Serve never reboots the server. The page shows when the server waits for a reboot, for example after a new kernel.
- An install that fails before it starts, or that a restart of Serve's worker cuts off, shows as failed. It doesn't block the next install.
- If an install on another server still runs after 60 minutes, the page says so. The package manager may still be running on the server, so check there before you try again.

## Terminal

The **Terminal** page opens a root shell on the server. On remote servers, commands run over SSH. On the main server, they run directly on the machine the dashboard runs on.

:::caution
Terminal commands can break the server and the services on it. On the main server they can break the dashboard too.
:::

You need the **Console** permission to open it. See [Teams](/docs/teams).
