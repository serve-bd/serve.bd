This page covers how people sign in to Serve and how you lock the dashboard down. It also covers the activity log and the encryption key that protects your secrets.

## Two-factor authentication

Each user can turn on two-factor authentication on their **Account** page. Serve then asks for a 6-digit code from an authenticator app when they sign in.

1. Go to **Account → Two-factor authentication** and choose **Enable**.
2. Confirm your password.
3. Scan the QR code with 1Password, Google Authenticator or any TOTP app.
4. Enter the code.
5. Store the backup codes somewhere safe.

Two-factor authentication protects password sign-in. You need a password to turn it on or off, so set one first if you only sign in through a provider.

The **Account** page also shows your signed-in devices, where you can sign out other devices, and your sign-in methods. Keep at least one sign-in method.

## Passkeys

A passkey signs you in with your device, like a fingerprint, face or security key, instead of a password.

1. Go to **Account → Passkeys** and choose **Add passkey**.
2. Type a name. Serve fills in the device for you.
3. Follow your browser. It saves the passkey under your email.

To sign in, choose **Sign in with a passkey** on the sign-in page, or pick the passkey your browser suggests in the email field.

- A passkey works only at the address where you made it, so make it on the dashboard address you use.
- Passkeys need `https`, or `localhost`.
- When only single sign-on is allowed, passkey sign-in is off.

## Single sign-on

Set up providers under **Settings → Sign-in**. Changes apply at once; nobody needs to restart anything.

| Provider | Use it for |
| --- | --- |
| GitHub | Sign in with a GitHub account. You can limit sign-in to members of a **GitHub organization**. |
| Google | Sign in with a Google or Workspace account. |
| Microsoft | Work and school accounts (Entra ID), from any organization or from yours. |
| GitLab | GitLab.com or a GitLab of your own. |
| Bitbucket | Sign in with a Bitbucket account. |
| OpenID Connect | Your company login, like Keycloak, Authentik, Okta, Auth0, Zitadel or Pocket ID. |

For each provider, create an OAuth app at the provider, add the callback URL that Serve shows, then paste the app's **Client ID** and **Client secret**. [Sign-in providers](/docs/sign-in) has the steps for each one.

:::note
Most providers only accept `https` callback URLs. Give the dashboard a domain with HTTPS in **Settings → General** first.
:::

If the dashboard is set to HTTP only but its domain also answers on HTTPS, for example behind a proxy that redirects `http://` to `https://`, Serve uses the `https://` address. This applies to sign-in callbacks, invite links and password reset links. If your GitHub or Google sign-in app has an `http://` callback URL, change it to the `https://` URL Serve shows.

### OpenID Connect fields

| Field | What to enter |
| --- | --- |
| **Issuer URL** | For example `https://login.example.com`. Serve reads its `/.well-known/openid-configuration`. |
| **Scopes** | Default: `openid email profile`. |
| **Provider** | Keycloak, Authentik, Okta and more: shows where the issuer is and names the button. |
| **Button text** | The label on the sign-in page. Default: the provider's name, or **Sign in with SSO**. |

### Who can sign in

Each provider has these rules:

- **Only allow emails from**: comma separated domains, like `example.com` or `*@example.com`. Subdomains count. Leave empty to allow any email.
- **Allow new accounts**: when off, only people who already have an account, or were invited, can sign in.
- **New accounts join**: the organization and role new accounts get.
- **Show on the sign-in page**: turn a provider off and it disappears from the sign-in page. Its settings stay.

## Turning off password sign-in

Under **Settings → Sign-in → Email and password** you can turn password sign-in off and allow only your providers. A Root admin must have linked one of those providers on their **Account** page first. Saved passwords stay, and people who are signed in now stay signed in.

If you lock yourself out, set this in `/data/serve/.env` and restart Serve:

```bash
SERVE_ALLOW_PASSWORD_LOGIN=1
```

While it is set, password sign-in stays on. Remove it again to go back to the setting in the dashboard.

## API access

The **API** card under **Settings → Security** controls the [REST API](/docs/api):

- **Allow API requests**: when off, every API call answers `503`, whatever the token. Tokens are kept and work again when you turn it back on.
- **Rate limit**: requests per minute for each token. The default is 200. Above it, calls answer `429` with a `Retry-After` header. `0` means no limit.

## Allowed addresses

**Settings → Security → Dashboard access** has an **Allowed addresses** list. Only these IP addresses can open the dashboard. Enter one per line, like `203.0.113.7` or `10.0.0.0/8`.

The list applies to the dashboard domain only, so set a dashboard domain first.

:::caution
Make sure the address you connect from is on the list before you save.
:::

The same page has a **Security review** that checks your setup each time you open it.

## Activity log

**Activity** in the sidebar is an audit trail of changes made in the organization: who did what, and when. Changes made through the [API](/docs/api) show up there too. Revealing the instance encryption key is logged as well.

## Encryption key

Serve encrypts secrets such as variable values, tokens and passwords with `SERVE_ENCRYPTION_KEY` from `/data/serve/.env`.

- The key is never in a backup.
- Without it, a restored Serve cannot read its secrets.
- **Settings → Backups → Show encryption key** shows it.

Keep it in a password manager. See [Instance backups](/docs/instance-backups).
