A deployment builds or pulls a new image, starts new containers and moves traffic to them. This page covers how Serve does that, how to trigger it and how to watch it.

## Strategies

Set the **Strategy** under **Settings → Deploy**.

| Strategy | What happens | Use it for |
| --- | --- | --- |
| Rolling | Start new containers, wait for the health check, switch traffic, then stop the old ones. No downtime | Most apps |
| Recreate | Stop the old containers first, then start the new ones | Apps that need a single writer, like apps using SQLite |

Some apps always stop first, even with **Rolling**: apps that publish host ports, and apps that keep data in a volume on a path the image declares. Two copies of them can't run at once, so they have a short downtime.

**Drain time** gives old containers time to finish in-flight requests before they stop.

### Pre-deploy command

The **Pre-deploy command** runs once in a container from the new image, with its variables, before traffic switches. Use it for database migrations:

```bash
npm run migrate
```

### Post-deploy command

The **Post-deploy command**, also under **Settings → Deploy**, runs once in the new version's first container, after the new version is live. It runs on the service's own server. Use it for work that needs the new version running, like warming a cache.

- If it fails or times out, the deploy log shows a warning. The new version keeps running.
- Rollbacks skip it.

## Health check

New containers must pass the health check before they get traffic. Set it under **Settings → Health check**.

| Field | What it does |
| --- | --- |
| Path | The HTTP path to check. Without a path, the deploy waits for the port to accept connections |
| Port | The port to check. Defaults to the app port |
| Interval | Time between checks |
| Timeout | Give up and roll back after this long |
| Start period | Wait before the first check |
| Expected status | Status codes that count as healthy, like `200-399`. Default: any status below 500 |
| Successes needed | How many checks in a row must pass |

## Deploy approvals

A project can make deploys wait until someone approves them. Turn it on under **Project settings → Deploys → Approvals** with **Deploys wait for approval**, for every environment or only the ones you pick.

Each service can change this in its **Approval** card, under **Settings → Deploy** for apps or **Settings → Compose** for stacks:

- **Follow the project**: the default.
- **Always wait for approval**.
- **Never wait**.

Only people who can approve deploys can change it.

### Who approves

Owners and admins can approve. Other roles need the **Approve deploys** permission. See [Teams](/docs/teams). Their own deploys start right away.

### What waits

Git pushes, deploy hooks, API calls and manual deploys by other people wait. A waiting deploy shows **Approve** and **Reject** on its deployment page and in the deployments list. The service card shows **Waiting for approval**. If a newer deploy comes in, it replaces the one that was waiting.

These never wait: rollbacks, the first deploy of a new service, databases and pull request previews.

To hear about waiting deploys, tick **Deployment waiting for approval** on a [notification channel](/docs/monitoring#events).

## Deploy freezes

A freeze stops deploys for a while, for example during a sale or at night. Set it under **Project settings → Deploys → Deploy freeze**.

- **Freeze deploys now**: for 1 hour, 4 hours, 24 hours, 3 days, 1 week, or until you turn it off. Add a reason if you like, so others know why.
- **Every week**: hours on chosen days, with a start and end time, in a time zone you pick. The hours can run past midnight. A weekly freeze covers every environment or the ones you pick.

During a freeze, pushes and deploy hooks are skipped, and the deployments list notes them. Manual deploys are refused. Rollbacks still work. If you approve a waiting deploy during a freeze, it starts when the freeze ends.

## Changes waiting for a deploy

Most settings apply on the next deploy. When you change one, the **Redeploy** button shows a dot until you deploy again. These changes count:

- Source, build and runtime settings.
- Database and Compose settings.
- Variables, and the shared variables the service uses.

Domains, maintenance and proxy settings apply on their own, without a deploy. They don't add the dot.

## Rollbacks

Each past deployment has a rollback button. It runs the image from that deployment again. Images kept for rollbacks survive server cleanup.

## Deploy on push

Turn on **Deploy on push** to deploy every time you push to the app's branch. Use **Watch paths** to deploy only when certain files change. See [Builds](/docs/builds).

Serve adds the webhook to the repository for you when it can. If it could not, the service shows a warning with a **Register webhook** button. You can also add it by hand: copy the **Git webhook URL** and **Webhook secret** from **Settings → Webhooks** into your Git host. The URL looks like this:

```text
https://serve.example.com/api/webhooks/git/<serviceId>
```

:::caution
Git webhooks need the dashboard on a domain with HTTPS. Set this up in **Settings → General**.
:::

If the dashboard is set to HTTP only but its domain also answers on HTTPS, for example behind a proxy that redirects `http://` to `https://`, Serve uses the `https://` address. This applies to GitHub App webhooks, repository webhooks, and the webhook and deploy hook URLs in **Settings → Webhooks**. A GitHub App moves to the new address within an hour, and whenever you change the dashboard domain settings.

Rotating the secret breaks existing webhooks and deploy hooks until you update them.

### Skip a deploy

A push does not deploy when its last commit message contains one of these markers, in any case:

```text
[skip ci]  [ci skip]  [no ci]  [skip cd]  [cd skip]  [skip deploy]  [deploy skip]
```

The deployments list records the push as skipped, for example "The commit message has [skip ci]". The same markers in a pull request title skip its preview. This works with GitHub, GitLab, Gitea and Bitbucket.

## Deploy hooks

A **Deploy hook** is a URL that deploys the latest commit when called. Use it from CI or any script. Find it under **Settings → Webhooks**. It accepts GET or POST.

Pass the secret as a query parameter:

```bash
curl -X POST "https://serve.example.com/api/deploy-hooks/<serviceId>?token=<secret>"
```

Or in the `x-deploy-token` header, which keeps it out of logs:

```bash
curl -X POST "https://serve.example.com/api/deploy-hooks/<serviceId>" \
  -H "x-deploy-token: <secret>"
```

The response holds the new deployment's ID:

```json
{ "ok": true, "deploymentId": "..." }
```

For more control, use the [API](/docs/api).

## Pull request previews

Serve can deploy each pull request as its own preview app. Turn on **Deploy pull requests** under **Settings → Previews**. Pull request events arrive through the same webhook as pushes. Pull requests from forks are never deployed.

### Open pull requests

The **Previews** tab lists the repository's **Open pull requests**. Previews start on their own for new pull requests. From this list, you can deploy previews for pull requests opened before previews were on, or deploy one again. Pull requests from forks are listed, but never deployed.

This works with GitHub, GitLab, Gitea and Bitbucket. Public repositories on github.com and gitlab.com work without a connected account.

In the [API](/docs/api): `GET /services/{id}/pull-requests` lists them, and `POST /services/{id}/pull-requests/{number}/preview` deploys one. Both need the `services.deploy` permission.

### Previews for Docker image apps

An app that runs a Docker image can have previews too. Your CI pushes a tag of the image, and Serve runs it next to the app, at its own address.

1. Turn on **Allow previews** under **Settings → Previews**.
2. On the **Previews** tab, choose **New preview**.
3. Enter a **Pull request** number and an **Image tag**, or a `sha256:` digest.

The same number again deploys the new tag to that preview. The URL template, preview variables and preview databases work as they do for apps from git. In the API: `POST /services/{id}/previews` with `{ "pr": 42, "tag": "pr-42" }`.

### Preview URLs

The **URL template** sets where each preview is reached. `{pr}` becomes the pull request number and goes in the first label, like `pr-{pr}.example.com`. If you enter `*.example.com`, the first label becomes `pr-{pr}`. Leave it empty for a generated address.

One wildcard DNS record, like `*.example.com`, pointed at the server covers every preview. If you use a Cloudflare Tunnel, or the DNS zone is in a connected Cloudflare account, each preview gets its own DNS record instead.

### Preview databases

By default, previews get the app's variables, so they use its production database. To avoid that, turn on **Copy a database for each preview**. When a pull request opens, Serve restores a fresh dump into a new database and deploys the preview against it. The copy is removed with the preview.

- **Database to copy**: the database in this environment to copy.
- **Variable**: the preview gets the copy's connection URL in this variable.
- **How**: **A branch** creates a second database inside the same database server, named `pr-<n>`. It is quick and runs nothing new. **A separate copy** creates a new database service for each preview and uses more memory.
- **Hide personal data**: for SQL databases, runs your **Clean-up SQL** on the copy after the restore, before the preview starts. If it fails, the copy is removed and the preview is not deployed.

## Logs and console

Each deployment has its build log. A service also has tabs for runtime logs, request logs and metrics. The console tab opens a shell inside the running container.

- **Logs**: for an app with more than one replica, pick one replica to see only its logs. The clock button hides or shows timestamps. On phones, timestamps start hidden.
- **Metrics**: request charts appear only for a service with a domain. Hover over or tap a request bar to see its numbers. If the service has no domain and its server collects no metrics, the tab is hidden.
