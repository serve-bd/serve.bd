Serve runs databases as services next to your apps. You pick an engine and a version, and Serve handles credentials, storage, backups and connection details.

## Engines

Choose **New service → Add a database** in a project.

| Engine | Versions | Default port |
| --- | --- | --- |
| PostgreSQL | `18-alpine` (default), `17-alpine`, `16-alpine`, `15-alpine` | 5432 |
| MySQL | `8.4`, `9`, `8.0` | 3306 |
| MariaDB | `11`, `10.11` | 3306 |
| MongoDB | `8`, `7` | 27017 |
| Redis | `8-alpine`, `7-alpine` | 6379 |
| Valkey | `8-alpine` | 6379 |
| ClickHouse | `25.8-alpine`, `latest` | 8123 |

### Custom images

You can use your own image for an engine, for example `pgvector/pgvector:pg17` for PostgreSQL with the pgvector extension.

## Settings

A database has these settings pages: **Details**, **Credentials**, **Initialization**, **Configuration**, **Runtime and network**, **TLS**, **Health check** and **Persistent storage**.

Depending on the engine, you can set:

- **initdb arguments** and **Host authentication** for PostgreSQL.
- **Character set** and **Collation**.
- Init scripts. They run in name order from `/docker-entrypoint-initdb.d`, only when the data directory is empty.
- A custom config file.
- **Extra server arguments**.

### TLS

Under **TLS**, turn on **Enable TLS** to encrypt connections. Serve creates a private certificate authority for the database. The **Mode** is **Prefer** (TLS when the client supports it) or **Require** (only TLS connections from outside, through the public port). Inside the private network, plain connections work in both modes. For Redis, the database then only accepts `rediss://` connections. TLS changes apply on restart.

For PostgreSQL, the private connection URL has no `sslmode`, in both modes. Some clients, like node-postgres and Prisma, read `sslmode` as "check the certificate", and the certificate names the database's domain, not its private hostname, so they would fail.

The public URL uses `sslmode=require`. node-postgres reads that as `verify-full`, so it needs the domain's certificate to be trusted, or `&uselibpqcompat=true` added to the URL.

## Connecting

### From other services

Services in the same environment connect over the private network. Copy the **Internal connection URL** from the database settings, or reference it from an app variable:

```text
DATABASE_URL=${{postgres.DATABASE_URL}}
```

Here `postgres` is the database service's name. Other services also reach the database at its **Private hostname**. See [Environment variables](/docs/environment-variables).

## Public access

A database's **Public access** page, under its settings, decides who can reach it from outside the project. It has a card for the database, a card for the [read replicas](#read-replicas) when it has some, and on PostgreSQL a card for the [pooler](#connection-pooling). Each card has the same parts.

The database's header shows only the public port, like `:15432`, not the server's address, so it stays private when you share your screen.

### Public port

Turn on **Public port** to connect from outside Serve, for example with a desktop client. While it is off, only services in the same project environment can connect.

- **Port**: leave it empty and Serve picks a free one. Once a port is set, it stays, because clients and firewalls point at it. To get a new port, turn public access off, save, then turn it on again.
- **Who can connect**: **Anyone with the password**, **Only some IP addresses**, or **Only this server** (`localhost`, or an SSH tunnel). **Only this server** isn't offered while the card has a domain.
- With **Only some IP addresses**, enter one address or range per line, like `203.0.113.7` or `198.51.100.0/24`. **Add my IP** adds the address you use now.

**Save and restart** applies the change.

:::caution
A public database port is open to the internet. Use a strong password, turn on TLS, and limit who can connect where you can.
:::

### Database domain

Give a database a domain, like `db.example.com`, so clients connect to it from anywhere with a real certificate. Type the domain in the **Domain** field of the **Public port** card and save. The card header then shows the certificate's state.

On a server with a public IP, Serve then does the rest:

- It opens the public port, or picks a free one when the port is empty.
- It turns on TLS and gets a Let's Encrypt certificate for the domain.
- If the domain's zone is in a connected [Cloudflare](/docs/cloudflare) account, it creates the DNS record. Otherwise, point an `A` record at the server's IP yourself.
- It restarts the database once, after the certificate is active, and shows the **Connection URL**.

If the server has no public IP, the card says so, and a domain can't reach the database.

Removing the domain turns off what it turned on. The public port stays. If TLS was on before you added the domain, it stays on.

:::caution[Keep the record DNS only]
In Cloudflare, the record must be **DNS only** (grey cloud). Cloudflare's proxy (orange cloud) does not carry database traffic. For the same reason, the zone's SSL/TLS mode, like **Full (strict)**, doesn't matter here.
:::

For PostgreSQL 16 and newer clients, add `sslmode=verify-full&sslrootcert=system` to the URL to also check the certificate. Other engines' clients check it by default.

Several databases on the same server can share one domain. Each keeps its own port. A domain can't lead to databases on different servers.

The certificate comes from Let's Encrypt through Cloudflare DNS when the zone is connected, or over HTTP otherwise, which needs the nginx proxy. If the server already has a certificate that covers the name, like an uploaded wildcard, Serve uses that one. It skips certificates that database clients do not trust: Cloudflare Origin CA certificates and uploaded certificates issued by Cloudflare.

If a certificate fails, Serve asks for it again once the domain points at the server. **Retry** on the card asks right away.

:::note[Cloudflare Tunnel]
Since v0.2.6, database domains no longer offer a Cloudflare Tunnel. A domain set up through a tunnel before keeps working until you change or remove it. Clients still connect to it with `cloudflared access tcp`. See [Cloudflare](/docs/cloudflare#databases-through-a-tunnel).
:::

### Pooler and replica access

The pooler and the read replicas have cards of their own, with a port, **Who can connect** and an optional domain. Over a public port, they accept TLS connections only. Inside the private network, plain connections still work.

- The pooler opens a port on the database's server.
- The replicas share one port on every server a replica runs on. By default it is the engine's port plus 12000, like `15306` for MySQL, when that port is free. Their domain gets an `A` record for each of those servers, and a certificate on each.
- On engines other than PostgreSQL, a replica domain needs [TLS](#tls) turned on for the database.

Pooler and replica domains lead only to servers with a public IP whose port answers from the internet. The card names the replicas the domain can't reach.

## Connection pooling

PostgreSQL databases can run a connection pooler, PgBouncer, in front of the database. Many app connections then share a few real ones. Turn it on under **Connection pooling** with **Enable connection pooling**. The database keeps running, and no data is touched.

The database's own URL stays the same. Apps opt in with the pooled URL:

```text
DATABASE_URL=${{postgres.POOLED_DATABASE_URL}}
```

| Setting | What it does |
| --- | --- |
| **Mode** | **Transaction**: a connection per transaction. Most efficient, but session features like `LISTEN`/`NOTIFY`, session advisory locks and `SET` for the whole connection don't work through it. **Session**: a connection per app connection. Everything works, with less saving. |
| **Database connections** | Real connections per database and login. |
| **App connections** | The most connections the pooler accepts. |

Logins added later work through the pooler too, because it checks them against the database. Other services reach the pooler at `POOLER_HOST`, the database's private hostname plus `-pooler`.

## Read replicas

A read replica is a live, read-only copy of a database, for heavy reads like reports and search. Writes still go to the database. Read replicas work with PostgreSQL, MySQL, MariaDB, MongoDB, Redis and Valkey. Add them under **Settings → Read replicas** with **Add replica**.

- A database can have as many replicas as you need. Serve sets no limit. When PostgreSQL needs more replication slots for them, Serve raises its settings.
- Each replica runs on a **Server**: the database's own server, or one that shares a [private network](/docs/private-networks) with it.
- Each replica first copies the database, then follows every change. Its status says **Copying the database**, then **Following, up to date**, or how many seconds behind it is. A copy that stops halfway starts again from the beginning. It is never left as a copy you can write to.
- Replicas run the exact image the database runs, down to its digest. So a tag that moved on Docker Hub can't split them.
- Replicas work over [TLS](#tls) too. Older database certificates are renewed with the same certificate authority, so MongoDB members can also use them as client certificates.

### Turning replicas on, per engine

| Engine | What happens the first time |
| --- | --- |
| PostgreSQL | Nothing. The database keeps running. |
| MySQL | Serve turns on GTIDs while the database runs. No restart. |
| MariaDB | The database restarts once, to start its change log. Serve asks first. |
| MongoDB | The database restarts once, to start its change log. Serve asks first. |
| Redis and Valkey | Nothing. The database keeps running. |

On MongoDB, the database and its replicas form the replica set `rs0`. Replicas join as members that never vote and never become primary on their own. Their URLs use `directConnection=true`, and the read URLs also set `readPreference=secondaryPreferred`.

Read replicas are tested on MySQL 8.0, 8.4 and 9, MariaDB 10.11 and 11, MongoDB 7 and 8, Redis and Valkey.

Apps read from the replicas with the read URL. It spreads reads over every replica:

```text
READ_DATABASE_URL=${{postgres.READ_DATABASE_URL}}
```

To use one replica only, use `READ_DATABASE_URL_1`, `READ_DATABASE_URL_2` and so on, after the replica's number. `READ_HOST` is the shared hostname of all replicas: the database's private hostname plus `-replica`.

Replicas on other servers stop, start and restart with their database. Moving a database to another server takes its pooler and replicas along. The database's **Logs** tab has a tab for the database, its pooler and each replica.

Removing a replica deletes its copy. Apps that read from it move to the other replicas, or lose the read URL if none are left. The database itself is not touched.

### Promote a replica

If the database's server is lost, **Promote** a replica to make it the database:

- The database stops, if its server still answers.
- The database starts again on the replica's server, with the replica's data. Changes the replica had not received yet are lost.
- The old data stays in its volume.
- The other replicas copy the new database again.
- Public access of the pooler and the replicas is turned off.

### Replicas in the API

- `GET /services/{id}/database/replicas` lists the replicas.
- `PUT /services/{id}/database/replicas` sets them.
- `POST /services/{id}/database/replicas/{replicaId}/promote` promotes one.

See the [API](/docs/api).

## Users

The **Users** tab adds database logins. Give each app, teammate or tool its own login, with only the access it needs. Users work with PostgreSQL, MySQL, MariaDB and MongoDB. The database must be running.

Choose **Add user** and fill in:

- **Name**: lowercase letters, digits and underscores, starting with a letter, up to 32 characters, like `app_reader`.
- **Password**: leave it empty and Serve makes a strong one, or set your own of 12 to 128 characters.
- **Access**: one of the levels below.
- **Databases**: the databases the access applies to. The main database is ticked by default.

| Access | Lets the user |
| --- | --- |
| **Read only** | Read the data. It can't change anything. |
| **Read and write** | Read, add, change and delete rows or documents. It can't change tables. |
| **Full access** | Everything in the chosen databases, including making and changing tables, collections and indexes. On PostgreSQL, tables of the main login keep their owner. |

From a user's menu you can:

- **Show connection URL**: the password, the URL on the private network for services in the project, and the public URL when the database has a public port or a domain.
- **Change access**: the new access replaces the old one on every database.
- **Change password**: Serve makes a new password. Apps that use the old one can't log in until you give them the new one.
- **Delete**: the login is removed and the data stays. On PostgreSQL, tables the user made are given to the main login.

### Users made outside Serve

The list also shows logins made in other ways, for example with SQL. Their own grants stay until you change their access. Serve doesn't know their password, so it can't show a connection URL until you change the password.

Serve's own login, branch logins and the users built into the database are shown with a lock. You can't change them here.

### Permissions

| Action | Needs |
| --- | --- |
| See the list of users | **View projects** |
| Show a user's connection URL | **View projects** and **See secret values** |
| Add a user or change its password | **Manage services** and **See secret values** |
| Change access or delete a user | **Manage services** |

Making a login or seeing its password gives access to the data, so those steps also need **See secret values**.

## Keep data after a delete

When you delete a database, the box **Also delete volumes and stored data** decides what happens to its data. If you leave it unticked, Serve keeps the data volume and remembers it. This works only for a database that was deployed at least once.

To use the kept data again, choose **New service → Database** and pick **Kept data of &lt;name&gt;** under **Start from**. The new database starts on that volume, with the user and password it had, on the server where the data is. Each kept data can start one database.

The volume then belongs to the new database. If you delete that database with the box ticked, the volume is deleted.

- Only the data volume is kept. Extra volumes from **Persistent storage** are not.
- When you delete a whole project, its volumes are deleted. Nothing is kept.

## Data

The **Data** tab shows what is inside the database. You can browse tables, run queries and edit rows. See [Browse and edit data](/docs/data).

## Branches

A branch is a full copy of a database's data that you can change freely. Use it to test a migration, debug with real data, or give a pull request preview its own database.

Open the database's **Branches** tab and choose **New branch**. The database must be running, and it keeps running while Serve copies the data. Each branch uses about as much disk as the main database. A database can have up to 20 branches.

In the **New branch** dialog:

- **Name**: lowercase letters, digits and dashes, up to 30 characters, like `feature-login`.
- **Copy from**: **Main data**, or a branch that is ready. A branch copied from another branch also resets from it.
- **Copy every database**: also copy the other databases on the same database server. See [Copy every database](#copy-every-database).
- **Hide personal data**: run your clean-up SQL on the copy. See [Hide personal data](#hide-personal-data).

Branches live inside the same database server. Each has its own login, so a branch can't change the main data.

Each branch provides these variables: `DATABASE_URL`, the engine's own URL (`POSTGRES_URL`, `MYSQL_URL`, `MONGO_URL` or `REDIS_URL`), `HOST`, `PORT`, `USERNAME`, `PASSWORD` and `DATABASE`. Reference them from any service in the environment:

```text
DATABASE_URL=${{postgres.branches.staging.DATABASE_URL}}
```

The page shows branches as a **List** by default. Switch to **Canvas** for a diagram of the main database, its branches, and the services that use each branch with the variable they read.

### Reset and delete

**Reset** replaces the branch's data with a fresh copy of its source. Changes made in the branch are lost. If the source branch was deleted, the reset copies the main data.

**Delete** removes the branch's database and login. Services that reference it lose their connection. If other branches copy from it, you can also delete them, which is ticked by default. If you keep them, they copy the main data on their next reset.

The database must be running to reset or delete a branch.

### Copy every database

A database server can hold more than one database. With **Copy every database**, the branch copies all of them. Each copy is named `<database>__<branch>`, for example `orders__staging`, and the branch's login can use all of them.

Each database gets its own reference. The list shows them as chips: click one to copy it.

```text
DATABASE_URL=${{postgres.branches.staging.databases.orders.DATABASE_URL}}
```

This works with PostgreSQL, MySQL, MariaDB, MongoDB and ClickHouse. Personal data is not hidden in these branches.

### Hide personal data

To keep real personal data out of a branch, write clean-up SQL. Choose **Hide personal data** at the bottom of the **Branches** card and save the SQL, for example:

```sql
UPDATE users SET email = 'user' || id || '@example.com', name = 'User ' || id;
DELETE FROM sessions;
```

Then tick **Hide personal data** when you create a branch. Serve runs the SQL on the copy right after copying, and again after every reset. If the SQL is missing or fails, the branch fails, so it never holds real data. These branches are marked **Personal data hidden**, and a branch copied from one hides the data too.

Clean-up SQL works with PostgreSQL, MySQL, MariaDB and ClickHouse. It can't be combined with **Copy every database**.

### Redis and Valkey

Redis and Valkey branches are database numbers 1 to 15 of the same server, so a database can have up to 15. They use the main password, so an app given a branch could still switch to the main data. For that reason, pull request previews can't use them.
