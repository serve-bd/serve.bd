The `serve` command is your Serve dashboard in the terminal. Deploy and roll back, follow logs, start and stop services, manage environment variables, domains and databases, and run your servers, team and integrations. It works the same in scripts and CI.

## Install

```bash
curl -fsSL https://serve.bd/cli.sh | sh
```

The same script is also at `https://raw.githubusercontent.com/serve-bd/serve/main/install-cli.sh`.

It installs the newest CLI to `/usr/local/bin` when it can write there, and to `~/.local/bin` otherwise. To install a given version, set `SERVE_CLI_VERSION`, like `SERVE_CLI_VERSION=v1.0.0` (`1.0.0` and `cli-v1.0.0` work too). The script checks the download against its SHA-256 checksum.

The CLI has its own versions, apart from Serve's. Its [GitHub releases](https://github.com/serve-bd/serve/releases) are tagged `cli-v1.0.0`, `cli-v1.1.0` and so on, and named "Serve CLI". Any recent CLI works with any recent Serve, so you don't need to match the two. CLI versions up to v0.3.x came with Serve's own releases and are still attached to them.

Each CLI release has downloads for Linux, macOS and Windows, named `serve_<version>_<os>_<arch>`, and a `checksums.txt`. On Windows, download the `.zip` for your machine and put `serve.exe` in your `PATH`.

With Go 1.26 or newer, you can also build it yourself:

```bash
go install github.com/serve-bd/serve/cli/cmd/serve@latest
```

## Upgrade

```bash
serve upgrade
```

This downloads the newest CLI for your machine, checks it against the release's `checksums.txt`, and replaces the `serve` you ran. It prints the old and the new version. When you already have the newest, it says so and changes nothing.

- `serve upgrade --check` only says whether a newer version is out.
- `serve upgrade --version v1.2.0` installs that version, newer or older.
- When `serve` is in a folder you can't write to, like `/usr/local/bin`, run `sudo serve upgrade`, or run the install script again.
- A build of your own (`serve version` says `dev`) is not replaced unless you pass `--force`.
- On Windows, the old binary is kept next to the new one as `serve.exe.old`. The next upgrade removes it.

`HTTPS_PROXY` is honored. `--insecure` and `SERVE_INSECURE` are not: they are for your dashboard's certificate, and a new binary always comes over checked HTTPS.

### The update notice

After `deploy`, `redeploy`, `rollback`, `init`, `link`, `status`, `login`, `logs` and `env pull` or `env push`, the CLI prints one line when a newer version is out:

```
  serve v1.2.0 is out (you have v1.1.0). Run: serve upgrade
```

It never slows a command down. The CLI asks GitHub at most once a day, in the background while the command runs, and remembers the answer.

It is never shown:

- when the output is not a terminal, like in a script or a pipe,
- with `--json`, or with `logs -f`,
- in CI (when `CI` is set),
- when `SERVE_NO_UPDATE_CHECK` is set. Set it to turn the notice off, like `export SERVE_NO_UPDATE_CHECK=1`. This also stops `serve version` from asking GitHub.

`serve version` shows the version, and always checks whether a newer one is out.

## Log in

```bash
serve login https://serve.example.com
```

The CLI shows a code and opens the dashboard in your browser. Check that the code matches, pick the organization and approve. The approval page also shows the address and time of the request, so you can tell it is yours. Sign-in codes are rate limited. A token named "CLI on &lt;computer&gt;" then appears on the **Keys & tokens** page, where you can revoke it.

- Without a browser, pass `--no-browser` and open the link on any device.
- To use a token you made yourself on **Keys & tokens**, run `serve login <url> --token <token>`.
- `serve whoami` shows the login, and `serve logout` logs out and revokes the token. If it can't reach the server to revoke the token, it says so. Then revoke it yourself on **Keys & tokens**.

### Several logins

Each login is a context:

- `serve context ls` lists them.
- `serve context use <name>` switches to one.
- `serve context rm <name>` removes one.
- `--context <name>` picks one for a single command.

A folder linked to a dashboard uses the context for that dashboard. Each saved token only goes to the address of its own context. The address in a folder's link only picks which saved login to use.

### In CI

Set both `SERVE_URL` and `SERVE_TOKEN` instead of logging in:

```bash
export SERVE_URL=https://serve.example.com
export SERVE_TOKEN=srv_...
serve deploy --yes --service web
```

`SERVE_URL` is usually the dashboard address. An API address that ends in `/api/v1`, like the one in the [API](/docs/api) examples, works too.

The token only goes to `SERVE_URL`, never to an address in a folder's link. With `SERVE_TOKEN` but no `SERVE_URL`, the CLI stops with "Set SERVE_URL with SERVE_TOKEN" and exit code `2`.

The CLI never asks a question without a terminal. Where it needs a choice, the error names the flag to pass.

### Self-signed certificates

For a dashboard with a self-signed certificate, pass `--insecure`, or set `SERVE_INSECURE=1`. `HTTPS_PROXY` is honored.

### Redirects

When a request carries a token, the CLI refuses to follow a redirect from `https` to `http`, to another host, or to another port on the same host. So a token never leaves for an address you didn't log in to. Sign-in requests carry no token, and still follow redirects.

### On the server that runs Serve

On that server, you don't need to log in. Run the CLI as root, like `sudo serve status`, and it signs in by itself as the `local` context. Serve keeps a "Server CLI" token for it in `/data/serve/cli.json`, which only root can read.

- `serve login <url>` signs in to another instance, and makes it the current context.
- `serve logout`, while `local` is in use, stops the automatic sign-in. The server's file is not changed.
- `serve login --local` or `serve context use local` switches back.

## Deploy a folder

```bash
cd my-app
serve deploy
```

The folder needs no git repository: the CLI uploads it as it is.

The first time, `serve deploy` offers two choices:

- **Create an app** for the folder, like `serve init`. The app's source is shown as **Deployed from the CLI**.
- **Link an existing app**, like `serve link`.

When it creates an app, the CLI also asks how to build it. It suggests a builder from the folder's files:

- **Dockerfile** when the folder has a `Dockerfile`.
- **Automatic** when it has a project file, like `package.json` or `go.mod`.
- **Static site** when it only has an `index.html`. The CLI then asks for the folder with the site's files.

Without a terminal, the suggestion is used. To choose yourself, pass `--builder` to `serve init`, with `auto`, `dockerfile`, `nixpacks`, `railpack`, `buildpacks` or `static`. `--publish-dir`, `--build-command` and `--start-command` set the other build fields. See [Builds](/docs/builds).

The link is saved in `.serve/project.json`, and `.serve/` is added to `.gitignore`. `serve unlink` removes the link.

Then the CLI packs the folder, uploads it, and streams the build log until the deployment ends. It builds like a git checkout: with the Dockerfile, or with the builder you set. See [Builds](/docs/builds). Press Ctrl+C during the build to cancel the deployment or stop watching it.

In a git checkout, the deployment also shows the commit, branch and message, and notes "+ local changes" when there are some.

### What is uploaded

A file is left out when any of these apply:

- **Git ignores it.** Every `.gitignore` from the repository root down counts, also the ones above a subfolder you deploy, plus `.git/info/exclude` and your global git ignore file. With git's `core.ignorecase=true`, these rules match in any case.
- **`.dockerignore` names it.** This is a second, separate filter. A `!` line in `.dockerignore` never brings back a file that git ignores.
- **It is always left out:** `.git`, `.serve`, `node_modules`, and env files: `.env`, `.env.*`, `.env-*`, `*.env` in any case, and `.envrc`. Pass `--include-env` to keep the env files.
- **It can't be sent:** links that point outside the folder, and files that can't be read. The CLI warns about them.

A `.serveignore` file in the folder you deploy, in the same format, replaces the git rules. Use it to send build output that git ignores. `.dockerignore` still applies on top. The deploy says which files it used, and warns about a rule it can't read.

A home folder, the root folder, or a folder with more than 5,000 files and no project file is not uploaded until you say yes. Without a terminal, pass `--yes`.

### Deploy flags

| Flag | What it does |
| --- | --- |
| `--message` | A message for the deployment |
| `--no-cache` | Build without the cache |
| `--no-wait` | Start the deployment, print its id and return |
| `--yes` | Answer yes to the questions |
| `--git` | Deploy the app's own git source instead of the folder |
| `--root <path>` | Upload a wider folder, for a service that builds from a base directory inside it |
| `--service <name>` | Deploy to this service instead of the linked one |
| `--env <name>` | Deploy to the service of the same name in another environment |
| `--include-env` | Also upload `.env` files |

In a monorepo, deploy a subfolder with `serve deploy apps/web`, or use `--root .` when the service's root directory is inside the folder.

A failed upload is tried twice more, but a deploy is never sent twice. If the answer gets lost after the whole upload went out, the CLI says so. Check `serve deployments` before you deploy again.

### Apps that deploy from git

You can also upload a folder to an app that deploys from git. The upload is a one-off: the next push deploys the git source again. The CLI warns you, and asks once per folder.

### Change the builder

`serve builder` shows how the linked app is built. On a terminal, it then lets you pick another builder.

- `serve builder railpack` changes the builder.
- `--publish-dir`, `--build-command` and `--start-command` change those fields. Without a builder name, the builder stays.

The change applies from the next deploy.

### Redeploy and roll back

Serve keeps the last 5 uploads of each service. `serve redeploy` uses them again, so it needs no new upload. `serve rollback` runs an earlier image again.

### Approve and reject

In an environment that [needs approval](/docs/deployments#deploy-approvals), a deployment waits until someone with the **Approve deploys** permission lets it go.

```bash
serve approve                    # the linked service's deployment that waits
serve approve <id> --wait        # approve it and follow the build
serve reject --reason "Wait for the migration on Monday"
```

Without an id, the CLI takes the deployment of the service that waits. When several wait, it asks which one. Without a terminal, it lists their ids. While deploys are frozen, approval is refused: approve once the freeze ends. `--reason` is shown with the rejected deployment, and is at most 500 characters.

## Projects and services

### Projects and environments

```bash
serve projects create shop --description "The web shop"
serve projects show shop         # its environments, and how many services each has
serve projects rename shop store
serve projects rm old-site --with-services
```

A new project starts with one environment, production. `serve projects rm` asks for the project's name, or pass `--yes`. `--with-services` deletes its services first, and `--volumes` also deletes their data.

`serve environments`, or `serve envs`, works on the environments of the linked project, or `--project`:

```bash
serve envs create staging                  # an empty environment
serve envs clone production staging        # a copy of every service, with its variables
serve envs deploy staging                  # deploy every service in it
serve envs rm staging                      # also deletes its services and their data
```

A clone gets generated addresses of its own (`--no-domains` to skip them), and custom domains stay with the original. Databases start empty unless you pass `--copy-data`. Nothing is deployed until you run `serve envs deploy`. A project always keeps at least one environment.

### Create and change services

`serve services create` adds an app to the linked project and environment, or to `--project` and `--env`. Pick one source:

```bash
serve services create --image nginx:latest --port 80 --deploy
serve services create --repo https://github.com/acme/api --branch main
serve services create --repo https://github.com/acme/private --git-connection acme
serve services create --dockerfile ./Dockerfile --name worker
serve services create --upload --name site    # then serve link and serve deploy
```

The name comes from the image or the repository unless you pass `--name`. `--server` picks the server. Nothing is deployed unless you pass `--deploy`, which follows the build log like `serve deploy`.

The other commands work on the linked service, the one you name first, or `--service`:

```bash
serve services rename web frontend
serve services clone api --env staging
serve services move api --server worker-2
serve services move api --env staging
serve services set --port 8080 --replicas 3 --healthcheck-path /health
serve services rm old-api
```

- `clone` copies the settings, variables, scheduled tasks (turned off) and a generated domain. `--copy-data` also copies a database's data. Nothing is deployed.
- `move --server` deploys the service on the new server and removes the old containers. Data volumes stay on the old server, so a database needs `--force`. Back it up first and restore it after.
- `move --env` moves the service with its variables and domains. A folder linked to it follows.
- `set` changes only the flags you pass: `--port` (`0` clears it), `--replicas`, `--start-command`, `--healthcheck-path` and `--auto-deploy=true|false`. They apply on the next deploy.

### Maintenance, stacks and containers

```bash
serve maintenance on --message "Back at 14:00 UTC" --allow 203.0.113.7
serve maintenance off
serve compose                     # the stack's compose file as Serve deployed it
serve containers                  # the service's containers
serve containers restart worker   # one container, by id, name or compose service
```

While the maintenance page is on, visitors of the service's domains see it. `--allow` lets IP addresses or ranges through. `serve containers restart` restarts one container without a new deployment.

### Run a command in a container

`serve exec` runs a command in a running container of the service and streams the output. It exits with the command's exit code, so it works in scripts.

```bash
serve exec -- ls -la /app
serve exec "env | sort"                 # one argument is a shell line
serve exec --replica 2 -- hostname
serve exec -s stack --container worker -- php artisan queue:restart
serve exec -s postgres -t -- psql       # -t for a program that needs a terminal
serve exec                              # an interactive shell
```

Without a command, you get a shell with a real terminal: colors, full screen programs and window resizing work. Database containers are set up for their client, so `psql` or `mysql` log in without a password. `serve exec` needs the **Console** permission. A service with host access, like bind mounts or privileged mode, needs an admin of the Root organization.

### Templates

```bash
serve templates                          # every one-click template
serve templates analytics                # search
serve templates show <id>                # its values; --compose prints its compose file
serve templates deploy <id> --env staging --set KEY=value
```

`deploy` creates the stack in the linked project and environment, deploys it and follows the log. Passwords and secrets are generated. When there is a terminal, the CLI asks for values the template leaves empty.

## Databases

Every `serve db` command works on the database you name first, like `serve db tables postgres`, on `--service`, or on the database next to the linked app. When there are several, it asks which one. Commands with an argument of their own, like `serve db backups restore <backup>`, take the database from `--service` or the link.

```bash
serve db create postgres                         # in the linked project and environment
serve db create mysql --project shop --env staging --version 8.4
```

`serve db create` takes postgres, mysql, mariadb, mongodb, redis, valkey or clickhouse. The name is the engine's unless you pass `--name`.

### Backups and imports

```bash
serve db backups                                 # newest first
serve db backups create --wait
serve db backups restore latest --wait
serve db backups restore <backup> --backup-first --yes
serve db backups rm <backup>
serve db backups restore latest --into staging-db --yes       # into another database
serve db backups restore latest --database shop --as shop=shop_copy
serve db backups restore latest --table public.orders        # only some tables
serve db backups test latest --wait                           # test-restore it
serve db backups download latest -o app.dump                  # checked against its checksum
serve db backups settings --schedule '0 3 * * *' --keep-monthly 12 --verify --users
serve db import ./dump.sql.gz --wait                          # upload a file
serve db import https://example.com/dump.sql.gz --wait
serve db import s3://backups/old/app.dump --wait # an S3 storage by name, id or bucket
```

A restore or an import replaces the data, so it asks for the database's name. In scripts, pass `--yes`. `--backup-first` backs up the current data before a restore. An import backs up first unless you pass `--no-backup`.

### Queries and tables

```bash
serve db tables
serve db query "select id, email from users limit 5"
cat report.sql | serve db query -
serve db query --write "update users set plan = 'pro' where id = 7"
serve db query cache 'GET "session:42"'          # Redis and Valkey take a command
serve db query mongo --collection users '{"plan": "pro"}'
```

Queries are read only unless you pass `--write`, which needs the **Manage services** permission and goes to the activity log. A query stops after 30 seconds and returns at most 1000 rows. A table cuts long values short, and `--json` gives them whole. These commands need the **Console** permission.

### Users, passwords, branches and replicas

```bash
serve db users create reporting --access read    # read, readwrite or owner
serve db users url reporting
serve db users password reporting                # a new password, printed once
serve db password --yes --show                   # change the main password
serve db branches create staging --wait          # a copy of the data
serve db branches reset staging
serve db replicas                                # state and lag of each read replica
serve db replicas promote <replica>
serve db dependents                              # services that use this database
```

Lists never show passwords. Only `serve db users password`, `serve db users url` and `serve db password --show` print them. After `serve db password`, the services that use the database get the new password on their next deploy, and the command names them.

`--wait` shows a spinner until the work ends. Ctrl+C only stops the waiting: the work goes on on the server.

## Domains, variables and more

### Domains

Besides `serve domains add` and `rm`:

```bash
serve domains generate                     # a free address on the server's wildcard domain
serve domains check shop.example.com       # where its DNS points
serve domains retry-cert shop.example.com  # after you fix DNS
serve domains set shop.example.com --primary
serve domains set www.example.com --redirect https://shop.example.com
serve domains set api.example.com --port 8080
```

`serve domains set` changes only the flags you pass. `--port 0` goes back to the service's own port, and `--no-redirect` serves the app again. `serve domains check` exits with `1` until the domain points at the server, so a script can wait for it:

```bash
until serve domains check shop.example.com; do sleep 30; done
```

### Shared variables

Shared variables live in the organization, a project or an environment. The service's own variables stay under `serve env`.

```bash
serve vars                                         # all three scopes, values hidden
serve vars set API_URL=https://api.example.com --scope project
serve vars set LOG_LEVEL=debug --scope environment --env staging --redeploy
serve vars unset OLD_KEY --scope project
```

`set` and `unset` need `--scope`, so a change never lands in the wrong place. They also need the `variables.view-secrets` permission, since they write the whole list back. Only an admin changes the organization's variables. `--redeploy`, with `--scope environment`, deploys the environment's services again.

`serve vars` used to be another name for `serve env`. Use `serve env`, or `serve variables`, for the service's own variables.

### Scheduled tasks

```bash
serve tasks create cleanup --schedule "0 3 * * *" --command "npm run cleanup"
serve tasks run cleanup --wait
serve tasks runs cleanup --last
serve tasks set cleanup --schedule "30 4 * * *" --timeout 2h
serve tasks set cleanup --disable
serve tasks rm cleanup
```

The schedule is five cron fields in the server's time. Quote it. `--timeout` is 1 hour when not set. `serve tasks run --wait` prints the run's output and exits with `1` when the run fails.

### Previews, tags, uptime and the deploy hook

```bash
serve previews                            # open pull requests and their previews
serve previews deploy 42 --wait
serve previews rm 42
serve tags set prod team-api              # the service's tags
serve tags create prod --color red
serve tags deploy prod                    # every service with the tag
serve uptime set /health --interval 30s
serve uptime check                        # exits with 1 when the service is down
serve webhook rotate                      # a new deploy hook URL
```

- For an app that runs an image, `serve previews deploy <number> --tag <image tag>` runs that tag as the preview.
- `serve tags deploy` skips services it can't deploy, like during a deploy freeze, and says which.
- `serve uptime set` sets back to the default every setting you don't pass. `--off` pauses the check.
- After `serve webhook rotate`, the old deploy hook URL stops working right away. It asks first, or pass `--yes`.

## Servers and the instance

These commands need more than a deploy token. Servers and SSH keys need an admin of the organization that owns the server, and a Root admin for the instance's own servers. Certificates need the **Manage integrations** permission, and `serve instance` needs a Root admin. When the dashboard refuses, the CLI says which role or permission is missing.

### Servers

```bash
serve ssh-keys add deploy                  # prints the public key to put on the server
serve servers add --host 203.0.113.10 --key deploy --wait
serve servers show eu-1                    # connection, status, proxy, alerts and services
serve servers validate eu-1 --install-docker --wait
serve servers alerts eu-1 --cpu 85 --disk 80
serve servers proxy eu-1 caddy --wait
serve servers cleanup eu-1
serve servers rm eu-1 --stop-services
```

`serve servers add` connects over SSH, checks Docker and starts the proxy. `--wait` follows the setup and says what to do when it fails.

`serve servers rm` asks for the server's name, or pass `--yes`. When services run there, say what happens to them:

- `--stop-services` stops and deletes them. `--delete-data` also deletes their data.
- `--keep-services` keeps them running, and Serve only forgets them. Serve's proxy and the server's Cloudflare tunnels go too, unless you pass `--keep-proxy` or `--keep-tunnels`.
- `--remove-tailnet-device` also takes the machine out of its tailnet.

`serve servers reset-host-key` forgets the saved SSH host key. Use it only after you reinstall the server.

### A shell on a server

```bash
serve ssh web-1
serve ssh web-1 -- df -h
```

`serve ssh` opens a root shell on a server, like its **Terminal** page. With a command, it runs it and exits with its exit code. It is for admins who manage the server, with a token that has the `admin` and `console.access` permissions. You don't need the server's SSH key.

### Tailscale and private networks

```bash
serve tailscale                            # tailnets and their servers
serve tailscale join web-1                 # Serve installs Tailscale and joins
serve tailscale join web-1 --command       # print a command to run on the server
serve tailscale leave web-1 --remove-device
serve networks create backend --server web-1 --server db-1
serve networks join cache-1 --network backend
serve networks leave web-1 --network backend
```

[Tailscale](/docs/tailscale) is for admins of the Root organization. `join` needs a server Serve reaches now. For one it can't reach, `--command` prints a one-time command to run on it as root. A server in another tailnet moves only with `--force`.

A server joins the [private network](/docs/private-networks) once, from its page in the dashboard. Then `serve networks` puts it in networks. `--network` can be left out when there is only one.

### Certificates and the instance

```bash
serve certificates request example.com www.example.com --wait
serve certificates upload --cert fullchain.pem --key privkey.pem
serve certificates renew example.com --wait
serve certificates auto-renew off example.com
serve instance update --check
serve instance update --wait
serve instance backups create --wait
```

A certificate is named by its id, its name or one of its domains. `serve instance update` backs Serve up first, and goes back to the old version if the new one does not start.

## Team and integrations

Commands that delete something ask you to type its name. Pass `--yes` to skip that. Without a terminal, `--yes` is required.

### Members, roles and tokens

```bash
serve org rename "Acme Inc"
serve invite ada@example.com --role developer    # prints the invitation link
serve members set ada@example.com --role admin
serve members set ada@example.com --projects shop,blog
serve roles create deployer --permissions projects.view,services.deploy,logs.view
serve roles set viewer --add logs.view
serve tokens rm "Old CI"
serve activity --limit 500 --project shop
```

An invitation goes by email when email is set up, and the CLI prints its link either way. Owner and Admin can't be changed. Developer and Viewer only take permissions. New tokens are made on **Keys & tokens**. When you revoke the token the CLI uses, it warns first, and you are logged out.

### Integrations

The CLI never prints a secret. Give one with a `--…-file` flag (`-` reads standard input), with `--secret-stdin`, or at the hidden prompt. A flag like `--password` works too, but stays in your shell history.

```bash
serve registries add mine --kind generic --host registry.example.com --username ci --password-file token.txt
serve s3 add backups --endpoint https://s3.example.com --bucket my-backups \
  --access-key-id <key id> --secret-access-key-file key.txt
serve notifications add team --type email --set to=ops@example.com --events deploy.failed,backup.failed
serve notifications test team
serve git repos <connection>
serve cloudflare dns set example.com A www 203.0.113.10 --proxied
serve cloudflare tunnels create web-1
serve log-drains add logs --kind http --url https://logs.example.com/ingest \
  --header Authorization --secret-stdin --all-projects < token.txt
serve log-drains test logs
```

- `serve notifications add --help` and `serve secret-managers add --help` list the types and their settings. Settings are `--set KEY=value` and `--set-file KEY=path`.
- Git and Cloudflare accounts are connected in the dashboard. `--account` picks the Cloudflare account when several are connected.
- `serve cloudflare tunnels rm` lists the domains that stop working, and asks for the server's name.
- A log drain sends the logs of `--projects`, `--services` or `--all-projects`. `test` sends one line and shows what the destination answered. See [Log drains](/docs/log-drains).

Commands that work on a service use the linked one, or the one you name with `--service <name or id>`. `serve <command> --help` shows every flag, with examples.

A mistyped command gets a hint, like `serve db bakups`:

```
Error: unknown command "bakups" for serve db. Did you mean serve db backups?
```

`serve env pull` writes the variables to a `.env` file, and `serve env push` sets the variables of a `.env` file. Other variables stay as they are. Use `-` for standard output or input.

### For scripts

Lists and show commands take `--json`, like `serve servers --json` or `serve projects show shop --json`. A few others say so in their help, like `serve approve` and `serve db create`. A command that doesn't print JSON refuses `--json` with exit code `2`, so a script never gets plain text where it expects JSON. The exit code tells what happened:

| Code | Means |
| --- | --- |
| `0` | Done |
| `1` | An error |
| `2` | A usage error, like a wrong flag |
| `3` | The deployment failed or was cancelled |

## API

The CLI uses the [API](/docs/api). These parts were added for it:

- `POST /services/{id}/deploy/upload` takes a raw `.tar.gz` of the folder. Query parameters: `message`, `commit`, `branch`, `dirty` and `noCache`.
- The `upload` source type, when you create or update an app.
- `offset` on `GET /deployments/{id}/logs`, to read a build log from where you stopped.
- `since` on `GET /services/{id}/logs`.

Other commands use routes like `POST /deployments/{id}/approve`, `POST /services/{id}/exec` and the terminal sessions behind `serve exec` and `serve ssh`. See [Console and more](/docs/api#console-and-more) on the API page.

Limits on uploads:

- An upload to an app with host access, like bind mounts or privileged mode, needs a Root admin.
- An upload with more than 1,000,000 entries, or a path name longer than 4,096 characters, is refused.
- Hard links in an upload are kept as links.
