When an app comes from a Git repository, Serve builds a Docker image from it on each deploy. You control how in **Settings → Build**.

## Builder

The **Builder** field picks how Serve builds the image.

| Builder | What it does |
| --- | --- |
| Automatic | Uses a Dockerfile if present, otherwise Railpack detects the framework |
| Dockerfile | Always builds from a Dockerfile |
| Nixpacks | Builds with Nixpacks. Nixpacks must be installed on the server |
| Railpack | Builds with Railpack. Serve downloads it on first use |
| Cloud Native Buildpacks | Builds with a buildpacks builder image |
| Static site | Builds the files and serves them with nginx |

### Nixpacks

When a Node.js project names no Node version, Serve builds it with Node 22. A project names a version in `engines.node` in `package.json`, in `.nvmrc`, `.node-version` or `.tool-versions`, or with a `NIXPACKS_NODE_VERSION` build variable.

### Cloud Native Buildpacks

Serve fills in a default **Builder image**. Paketo builders also work. A builder image from another publisher needs an admin of the Root organization.

The builder decides how to install and build, so the install and build commands are not used. The start command is optional.

## Automatic builds

With **Automatic** and no Dockerfile, Serve builds with [Railpack](https://railpack.com), which reads the repository and picks the framework and its commands.

| Kind | Examples | How it runs |
| --- | --- | --- |
| Single-page and static sites | Vite (React, Vue, Svelte), Astro, Create React App, Angular, React Router | Built, then served by Caddy. Links to client-side routes like `/about` work |
| Node.js servers | Next.js, Nuxt, Express, NestJS, Fastify, Hono | The `start` script, else the `main` field of `package.json`, else `index.js` |
| Other languages | Python (Django, FastAPI, Flask), Go, PHP (Laravel), Ruby (Rails), Java, Rust, Deno, Bun | Railpack's defaults for each |

Serve adds what Railpack does not find on its own: a SvelteKit app with the Node adapter starts with `node build`, and a `start:prod` script (NestJS) is used over `start`.

The app gets `PORT` and should listen on it. An Astro site needs its `astro.config.mjs` to be detected as a static site.

Apps that were already deploying with **Automatic** before Railpack became the default keep building with Nixpacks, so they build the same way as before. The Builder field says so; pick **Railpack** to switch.

If detection picks the wrong thing, set the install, build or start command yourself, or add a Dockerfile.

## Static site builder

**Static site** builds the front-end with its own build script and serves the output folder with nginx, with links to client-side routes going to `index.html`. Without a `package.json`, the folder (or the **Output directory**) is served as it is.

## Build fields

| Field | What it does |
| --- | --- |
| Builder | How the image is built, see above |
| Root directory | The folder in the repository to build from, for monorepos |
| Dockerfile path | Where the Dockerfile is, if not at the root |
| Install command | Overrides the detected install step |
| Build command | Overrides the detected build step |
| Start command | The command the container runs |
| Output directory | Where the built static files are |
| Target stage | The stage to build in a multi-stage Dockerfile |
| Build arguments | Passed as `--build-arg`. Use variables marked build time for secrets |
| Build timeout | Stops a build that runs too long |
| Always build without cache | Skips the Docker build cache on every build |
| Git submodules | Checks out submodules before building |
| Watch paths | Only deploy on push when these paths change |

## Git LFS

If the repository's `.gitattributes` uses Git LFS, Serve fetches the LFS files before it builds. Only services of the Root organization fetch them. Other organizations get the small pointer files instead, for safety. If `git-lfs` is missing, the deploy log warns.

## Commit variables

Apps get these variables at runtime:

| Variable | Value |
| --- | --- |
| `SOURCE_COMMIT` | The commit that was built |
| `SERVE_GIT_COMMIT` | The same commit |
| `SERVE_GIT_BRANCH` | The branch |

A Dockerfile gets `SOURCE_COMMIT` as a build argument when it declares it:

```dockerfile
ARG SOURCE_COMMIT
```

Builds that don't declare it keep their cache when the commit changes.

## Reusing a built image

If a deploy is for a commit that was already built, with the same build settings, build variables, platform and Serve version, Serve reuses that image and skips the build. The deploy log says so. The image must still be on the build server. To build anyway, choose **Deploy without cache** under **Settings → Build**, or turn on **Always build without cache**.

## Build server and registry

By default an app builds on the server that runs it. Builds need memory, so you may want to build somewhere else. Open **Settings → Servers & registry** and pick a **Build server**.

You can also push each built image to a registry. Pick a saved registry and set a **Tag** pattern. These placeholders are available:

| Placeholder | Value |
| --- | --- |
| `{commit}` | Full commit hash |
| `{short}` | Short commit hash |
| `{deployment}` | Deployment ID |
| `{branch}` | Branch name |
| `{service}` | Service name |
| `{date}` | Build date |

Turn on **Also tag as latest** to push a `latest` tag too. When you add [extra servers](/docs/several-servers), they all run the same image.

A registry is optional. Without one, Serve builds once and copies the image from the build server to every other server on each deploy. With a registry, each server pulls the image instead, which is faster for big images and many servers. An image only runs on the CPU type it was built for. So when the app runs on servers of another CPU type (ARM servers next to Intel or AMD ones), one of those servers builds the image from the same commit, at the same time as the main build. The other servers of that type copy the image from it. With two ARM and two AMD servers, there are two builds side by side, and the other two servers only copy.

## Watch paths

With **Deploy on push** on, every push to the branch starts a deploy. **Watch paths** limits that to pushes that change certain files. This helps in a monorepo where several apps share one repository. Set up deploy on push in [Deployments](/docs/deployments).

:::tip
Builds need at least 2 GB of RAM. If builds fail on a small server, move them to a separate build server.
:::
