Environment variables pass configuration and secrets to your app. Serve stores them per service, lets you share them across services, and can read them from an external secret manager.

## Build time and runtime

Each variable can be available at build time, at runtime, or both.

- **Build time** variables are available while the image builds. Use them for things like API keys a build step needs.
- **Runtime** variables are set in the running container.

## Bulk edit

Use **Variables as .env** to edit all variables at once in `.env` format. Paste in an existing `.env` file to import it.

```text
DATABASE_URL=postgres://user:pass@db:5432/app
NODE_ENV=production
```

## Literal and multiline values

Each row on the **Variables** page has a menu (**…**) with two options:

- **Literal value**: the value is kept exactly as written. Text like `${{...}}` in it is never filled in, never looked up in a secret manager, and never drawn as a link. Use it for values that contain that text on purpose.
- **Multiline value**: a large text box, for keys and certificates. Values with line breaks get it on their own.

In the [API](/docs/api), set `literal: true` or `multiline: true` on the variable.

## Shared variables

You can define variables once and use them in many services. There are four levels:

- **Environment variables**: shared by services in one project environment, like production or staging.
- **Project variables**: shared by every environment in a project.
- **Organization variables**: shared by every project in the organization.
- **Server variables**: values per server. See [Server variables](#server-variables).

Set environment variables in the project's settings under **Shared variables**. Project and organization variables live on the **Shared variables** page under **Organization**. A service uses a shared variable by reference, added on the service's **Variables** page:

```text
KEY=${{environment.KEY}}
```

Shared variables reach an app only by reference. A shared variable can also hold a reference itself. For example, set the environment variable `DATABASE_URL` to:

```text
DATABASE_URL=${{postgres.DATABASE_URL}}
```

An app then pulls it in with:

```text
DATABASE_URL=${{environment.DATABASE_URL}}
```

### Server variables

Server variables hold values that depend on the server, like a region name or a path on the disk. Set them under **Organization → Shared variables → Servers**. Only organization admins can change them.

They belong to a server and an organization together. A server shared by several organizations gives each one its own values. Reference them like this:

```text
REGION=${{server.REGION}}
```

A service uses the values of its own server. Apps that also run on extra servers use the values of their main server. **Redeploy affected services** works here too, as on the other levels.

If a service is named `server`, `${{server.KEY}}` still reaches that service for keys the server has no variable for.

## References

A variable's value can reference other values. Serve resolves them when the service deploys.

| Syntax | Resolves to |
| --- | --- |
| `${{KEY}}` | Another variable on the same service |
| `${{service-name.KEY}}` | A variable on another service in the project |
| `${{environment.KEY}}` | An environment variable. `${{shared.KEY}}` also works |
| `${{project.KEY}}` | A project variable |
| `${{org.KEY}}` | An organization variable. `${{team.KEY}}` also works |
| `${{server.KEY}}` | A variable of the service's server |
| `${{replica.index}}` | The replica's index |
| `${{replica.number}}` | The replica's number |
| `${{replica.count}}` | How many replicas run |
| `${{postgres.branches.<name>.DATABASE_URL}}` | The URL of a PostgreSQL branch |
| `${{secrets.<provider>.<path>:<FIELD>}}` | A secret from a secret manager |

For example, to give an app the connection URL of a database service named `postgres`:

```text
DATABASE_URL=${{postgres.DATABASE_URL}}
```

### Database variables

A database service provides these variables:

| Variable | Value |
| --- | --- |
| `HOST` | The database's private hostname |
| `PORT` | Its port |
| `USERNAME` | The main user |
| `PASSWORD` | The main user's password |
| `DATABASE` | The main database |
| `DATABASE_URL` | The connection URL |
| `POSTGRES_URL`, `MYSQL_URL`, `MONGO_URL` or `REDIS_URL` | The connection URL, named after the engine |

PostgreSQL URLs use the `postgresql://` scheme. Some libraries, like Tortoise ORM, only accept `postgres://`. For them, build the URL from the parts:

```text
DATABASE_URL=postgres://${{postgres.USERNAME}}:${{postgres.PASSWORD}}@${{postgres.HOST}}:${{postgres.PORT}}/${{postgres.DATABASE}}
```

## Built-in variables

Serve sets these in every app container.

| Variable | Value |
| --- | --- |
| `SERVE_PUBLIC_URL` | The app's public URL |
| `SERVE_PUBLIC_DOMAIN` | The app's public domain |
| `SERVE_PUBLIC_URL_<SERVICE>` | The public URL of another service |
| `SERVE_PUBLIC_DOMAIN_<SERVICE>` | The public domain of another service |
| `SERVE_PRIVATE_DOMAIN` | The app's private hostname |
| `SERVE_SERVICE_NAME` | The service name |
| `SERVE_REPLICA_INDEX` | This replica's index |
| `SERVE_REPLICA_COUNT` | How many replicas run |
| `SOURCE_COMMIT` | The commit that was built, for apps from git |
| `SERVE_GIT_COMMIT` | The same commit |
| `SERVE_GIT_BRANCH` | The branch |

## Compose files that ask for a value

A Compose file can mark a variable as required with `${VAR:?message}`. If the value is empty, Serve stops the deploy before it starts, with the file's message, like "The compose file needs a value for ADMIN_EMAIL". The **Variables** page warns about it before you deploy. A variable that is not set at all was already caught.

## Secret managers

Instead of storing a secret in Serve, you can read it from a secret manager. Add one under **Integrations → Secret managers**. Serve supports:

- **HashiCorp Vault / OpenBao**
- Infisical
- Doppler
- **AWS Secrets Manager**
- AWS Parameter Store

Then reference a secret in any variable, using the name you gave the secret manager:

```text
DB_PASSWORD=${{secrets.prod-vault.app/db:password}}
```

Serve reads the secret from the provider each time the service deploys and never stores it.

## Per-replica variables

When an app runs several replicas, you can give a replica variables of its own. A replica without its own variables uses the service variables.

To make a value differ in each replica, pick **This replica** in the reference list. It offers `index`, `number` and `count`. This is useful to shard a bot or split work:

```text
SHARD_ID=${{replica.index}}
```

Your code can also read `SERVE_REPLICA_INDEX` and `SERVE_REPLICA_COUNT`.

:::note
Who can see variable values depends on the role. Developers can edit variables but can't see secret values unless their role allows it. See [Teams](/docs/teams).
:::
